# 案例 14：DDP 和 FSDP 对不上，一路查到词嵌入反向的一次 scatter-add

纯数据并行（DDP）和 FSDP 的 loss 差不在 0 上下。在混元 4 上一样一样地试，问题收窄到一个张量：词嵌入梯度。为什么偏偏是它，前后换了三种解释，最后落到 TPU 后端对一次 scatter-add 的处理方式上。

> **状态：机理已查明，三种修法都已合并（最后一个在 2026-11-11）。** 生产尺寸上的验收还没回来。

> **第二阶段：** 其余参数仍是纯数据并行、只把词嵌入表沿数据并行轴切开（`embedding_shard_over_data`），编译器就对这张表生成 FSDP 那条「先传后加」的路径：精度和第一版两种修法一样修好，词嵌入的跨卡通信少 93%，步时不增加。见[第二阶段](#第二阶段只把词嵌入表沿数据并行轴切开)。

## 先看结论：高频词 × 不排序

词嵌入的反向是一次 scatter-add：每个 token 把自己的梯度加回词表里自己那一行。表是 BF16，所以每一行的梯度是一串 BF16 加法。精度丢不丢，要两个条件同时成立：

- **这一行加了很多次。** BF16 每舍一次都有误差，加的次数越多积得越多。低频词一行只加几次，怎么加误差都小；高频词在一张卡、一个微批里要加几十到几百次（这一步最高频的 39 个词，中位数 74 次，最多 458 次，统计口径见第七幕）。
- **后端没有先排序。** 不排序时，同一个词的更新散在整串下标里，后端每碰到一次就把那一行 BF16 读出来、转 FP32 加上、舍回 BF16 写回，加一次舍一次。排好序时，同一个词的更新挨在一起，后端在片上的 FP32 缓冲里一口气加完，最后只舍一次。

后一种写法有个前提：excess precision 开着。它是编译器允许把中间结果留在 FP32、少舍几次的开关，默认开。

单拿这一个 scatter-add 在 v5p 上实测，一次 4096 个下标（纯数据并行每张卡一个微批是一条 4096 个 token 的序列，就是这么多），下标取真实 token。按「这一行在这次 scatter 里出现几次」分组，看离 FP64 的相对误差：

| 这一行出现几次 | 行数 | 不排序 | 排序 |
|---|---|---|---|
| 1 次 | 961 | 0 | 0 |
| 2–9 次 | 402 | 2.70e-3 | 1.72e-3 |
| 10–99 次 | 60 | 7.81e-3 | 1.66e-3 |
| ≥ 100 次 | 3 | 1.46e-2 | 1.70e-3 |

- 不排序那一列随次数一路涨；排序那一列不管出现几次都停在 1.7e-3 上下，那是最后一次舍入。
- 出现 1 次的行只是把一个 BF16 数加到 0 上，没有舍入，两边都是 0。
- 更新量是随机 BF16，这张表只比同一行的两列，不和后面训练里的数直接对。数据在 [`emb-scatter-sort-probe-tpu.json`](../alignments/04-tpu-self/results/emb-scatter-sort-probe-tpu.json) 里 `cells.4096` 各格的 `by_count`。

两种并行恰好落在两列。TPU 后端会在一次 scatter 的下标数超过词表行数的 1/8 时自动插排序（混元 4 词表 120832 行，门槛 15104；这条规则是用实验二分出来的）。

- **FSDP：过线，被排序。** 这里的词表按隐藏维切（1024 维，每张卡管 128 维），不是按词切。编译器自动切分时，让每张卡只算自己那 128 维的梯度，为此要把这个微批里 8 张卡的全部 token 收齐，所以每张卡那次 scatter 收的是 32768 个下标。这和 PyTorch FSDP「各卡先算整张表的梯度、再 reduce-scatter」的做法不同。
- **纯数据并行：不过线，不排序。** 每张卡有整张表，只对自己的 4096 个 token 做 scatter，再跨卡求和。

合起来是一张 2×2。格子里是训练第 1 步的实测：词嵌入梯度按行分组，离 FP64 的相对误差（第七幕的表）：

| | 低频行（10872 行） | 高频行（39 行，占梯度范数平方的 0.90） |
|---|---|---|
| 排序，只舍一次（FSDP 8） | 7.77e-3–9.31e-3 | 3.26e-3 |
| 不排序，加一次舍一次（纯数据并行 8） | 8.31e-3–9.41e-3，不明显 | **1.57e-2，丢** |

所以 FSDP 不差、纯数据并行差：高频行差 4.8 倍，低频行几乎不动。低频行的绝对误差反而大，那部分在 scatter 之前就有，两种写法一样，不是这里的问题。跨卡那次 BF16 求和是次要的（第七幕）。

修法是让这次累加落在 FP32：打开 `embedding_grad_fp32`，或只在本卡用 FP32、跨卡仍用 BF16 的 `embedding_grad_fp32_local_bf16_comm`。两者 300 步都在噪声内；1000 步 r 1.09、1.07，判「略超」，但没超过纯噪声自己能到的水平，和 GPU 重跑分不开。（r 是差 ÷ GPU 重跑的噪声上限：≤ 1 在噪声内，1–2 略超，> 2 超。）步时多 0.6–0.8 个百分点：不修时纯数据并行比 FSDP 快 3.4%，修后仍快 2.6–2.8%。

第二阶段换了个思路：其余参数照旧纯数据并行，只把词嵌入表沿数据并行轴切开（`embedding_shard_over_data`），编译器就对这张表走 FSDP 那条「先传后加」、排好序再加的路径。精度一样修好（1000 步 r 1.15，和 GPU 重跑分不开），词嵌入的跨卡通信反而少 93%，步时和不修一样。按目前的实测，这是三种做法里最好的一种（[第二阶段](#第二阶段只把词嵌入表沿数据并行轴切开)）。

**在自己的模型上怎么做：**

1. 纯数据并行时，首选打开 `embedding_shard_over_data`（第二阶段）。它依赖每张卡那次 scatter 的下标数过排序门槛（切分组里所有卡一个微批的 token 数超过词表行数的 1/8）；不过线时改用 `embedding_grad_fp32`，并用 MaxText `d5c9b113` 之后的代码，更早的代码在「数据并行 + 梯度累积」下会丢掉前面微批的梯度（第五幕）。
2. excess precision 保持默认开，`XLA_FLAGS` 里不要有 `--xla_allow_excess_precision=false`。照 10 月的建议关掉过的，要重新打开：在混元 4 上关掉它会让 FSDP 也每次舍，比纯数据并行还差（[第八幕末尾](#回头看-10-月的建议)）。
3. 想知道没开修法的旧跑法有没有中招，比较每张卡一次词嵌入 scatter 的下标数和词表行数的 1/8，见[第九幕](#第九幕结论和做法)的自查表。

**还没定的：** 生产尺寸上的验收还没回来；v7x 上同样判「超」（第 1 步词嵌入梯度同样变远），但机理只在 v5p 上实测过；排序门槛是在一个 libtpu 版本上测的。另外，两种并行编出的是两个程序，求和顺序不同，逐位相同做不到。

## 怎么查到的

下面按时间顺序讲排查经过。修法和代价也可以直接看[影响逐件「纯数据并行」](../alignments/04-tpu-self/impacts/01-data-parallel.md)，逐个 all-reduce 的证据在 [B1 梯度的跨卡归约](../alignments/04-tpu-self/b1-grad-reduction.md)。

## 第一幕：曲线不在 0 上下

起点是一次实际排查提出的两个要求：要一个确认没问题的 TPU 基线，好和 GPU 对精度；还要确认换并行方式以后，loss 和纯 DDP 的差在 0 上下波动。附图是 FSDP 8 减 DP 8 的 loss 差，2000 步累计下来最大到 0.01 量级。

10 月先在一个 6 层的测试模型（DeepSeek-V2 结构）上查，找到三个来源：

| 来源 | 量级 | 处理 |
|---|---|---|
| 初始权重随并行方式变化（随机数生成器按切分方式生成） | 2000 步末段 0.01–0.02 | 加 rng 开关 |
| excess precision 默认开，融合内部跳过中间的 BF16 舍入 | v5p 上 FSDP 前约 100 步偏低约 −7.9e-4 | 关 excess precision |
| ZeRO-1 + 梯度累积时梯度累加器是 BF16 | 前 100 步约 +3.0e-4 | 那条路径改 FP32 |

三项都处理后，测试模型上 v5p 的差回到噪声内（v7 上加了 rng 开关后 FSDP 仍略高，还要在 FSDP 一侧关 collective matmul）。但留了两个缺口。一是这些结论只在测试模型上验证过，还要在生产模型上再核。二是「FSDP 与 DDP 逐位相同」做不到：v5p、v7x、B200 上两种并行第一步就不同，第一处不同在第一层注意力后的 RMSNorm 输出。

## 第二幕：换到混元 4，纯数据并行超出噪声

混元 4 的 TPU 自比里，同一个模型（hy4-mini）、同一份权重和数据，每次只改一样东西，和 golden（当基准的那次运行：FSDP，8 卡）比。尺子是 GPU 同设置重跑的噪声上限 N，r = 差 ÷ N。

纯数据并行这一项判「超」（[实验矩阵 B 类](../alignments/04-tpu-self/MATRIX.md#b--并行与切分)）：

| 条件 | 曲线最差 r |
|---|---|
| 8 卡，每步两个微批（和 golden 一样） | 2.62 |
| 8 卡，不做梯度累积 | 3.69 |
| 16 卡 | 2.65 |
| v7x，8 个设备 | 2.21 |

四种条件都判「超」（r > 2）。其中 v7x 的 2.21 没超过 GPU 自己重跑能到的最大值 2.47（GPU 同设置 8 份轮流当被测的留一法，见 [04 设置](../alignments/04-tpu-self/setup.md)），单看曲线和 GPU 重跑分不开；把它和 GPU 重跑分开的是第 1 步：词嵌入梯度 R 3.54（判法见第三幕）。其余三种条件的曲线 r 都超过 2.47。8 卡那一行方向固定：TPU 的主 loss 持续偏高（带符号均值 +5.58e-6，r 1.85），梯度范数持续偏低（带符号均值 −2.60e-4，r 2.62，[尺子 1.7 节](../../../docs/guide/ruler.md)）。同一张表里，换张量并行、专家并行、混合切分都和 GPU 重跑分不开。问题不在「换了并行方式」本身，而在纯数据并行特有的某个地方。

## 第三幕：第 1 步对 FP64，只有一个张量远

曲线只能说「有系统偏差」，说不出偏差在谁身上。于是拿第 1 步的 205 个参数梯度，各自和 CPU 上用 FP64 重算的精确值比，给每个张量定责：离精确值不比 golden、GPU 远，就只是换了求和顺序（已定责）；比两者都明显更远（超过 1.2 倍），就是哪里丢了精度（未定责）。

结果很干脆：205 个里只有词嵌入梯度丢了精度。它离 FP64 1.51e-2，golden 是 4.00e-3、GPU 是 4.17e-3，比两者里较远的 GPU 还远 3.6 倍（R 3.62；只对 golden 比是 3.77 倍）。其余 204 个都在噪声内或只是换了顺序（6 个 iHC 小参数数值上病态，向来不定责，另算），离 FP64 的比值（纯数据并行 ÷ golden）中位数 0.99（[`ts-dp8-vs-golden.json`](../alignments/04-tpu-self/results/ts-dp8-vs-golden.json) 的 `step1_rows`，[尺子 2.4 节](../../../docs/guide/ruler.md)）。

范围从 205 个张量缩到 1 个。

## 第四幕：第一个假设，BF16 跨卡求和

最顺手的解释是：FSDP 下词嵌入表按隐藏维切，每张卡只管自己那 128 维，不跨卡求和；纯数据并行下每张卡有整张表，梯度要在 8 张卡之间加起来，而这次 all-reduce 用的是 BF16 加法。

修法也现成。`embedding_grad_fp32` 这个开关早就有（[变更台账](../CHANGES-LEDGER.md) M12），原本是为 GPU ↔ TPU 对齐加的：前向时从 FP32 主权重表里取行再转 BF16，而不是先把整张表转成 BF16 再取。前向逐位不变，反向的累加就落在 FP32 上。

## 第五幕：打开 FP32 开关后 r 611

打开这个开关、仍是纯数据并行 + 梯度累积 2，结果不是变好，而是 r 611（[实验矩阵「B1b」](../alignments/04-tpu-self/MATRIX.md#b1b-数据并行--embedding_grad_fp32词嵌入梯度丢了一块)）：

- 第 1 步词嵌入梯度范数只有 golden 的 0.51 倍；golden 里有梯度的 10911 行中，2829 行（2.6e-1）整行为 0，离 FP64 远 130 倍；
- 第 1 步梯度范数（裁剪前）6.19，golden 6.36。

一块梯度凭空没了。去看编译出来的训练步程序：编译器把这份 FP32 梯度的 all-reduce 挪出了梯度累积循环，同时在循环里每次迭代都把 0 号以外各张卡（编译器叫「分区」）的累加器清零（[B1 梯度的跨卡归约](../alignments/04-tpu-self/b1-grad-reduction.md)第五节）。

```
// 循环体内
%partition-id.247 = u32[] partition-id()
%convert.6873 = pred[] convert(%partition-id.247)
%broadcast_select_fusion.436 = f32[120832,1024] fusion(%wide.wide.param.2#254, %convert.6873), ...
    //   即 select(partition-id != 0, 0, 累加器)
%scatter_fusion = f32[120832,1024] fusion(%broadcast_select_fusion.436, %bitcast.26476, %convert.6875), kind=kCustom
// 循环外
%all-reduce.521 = f32[120832,1024] all-reduce(%while.2471#254), ...
```

结果是 0 号卡留下两个微批的梯度，其余 7 张卡只剩最后一个微批的。

这个 bug 要三个条件同时成立才出现：数据并行、梯度累积 > 1、开这个开关。去掉任何一个都和 GPU 重跑分不开：FSDP 8 + 累积 2 + 开关 r 1.02；数据并行 8 + 累积 1 + 开关 r 1.01（[实验矩阵「已修」](../alignments/04-tpu-self/MATRIX.md#已修)）。

修法是 MaxText 上的一处修改（提交 `d5c9b113`）：三者同时成立时，每个微批累加前加一个 `optimization_barrier`，挡住这次挪动。验证：

| 运行 | 结果 |
|---|---|
| golden 用修复后的代码重跑 | 逐位相同，程序相同 |
| 数据并行 8 + 累积 2 + 开关 | 词嵌入梯度离 FP64 3.79e-3（golden 4.00e-3）；第 1 步梯度范数（裁剪前）6.3596（FP64 6.3594）；300 步 r 0.98，1000 步 1.09 |
| 16 卡纯数据并行 + 开关 | 300 步 r 0.99，1000 步 1.30 |

这个修法有效，但它同时改了本卡累加和跨卡求和，没有证明主因在跨卡求和。

## 第六幕：追问，本卡 FP32、跨卡 BF16 行不行

接着有人追问：既然毛病在 BF16，能不能只把本卡的累加换成 FP32，跨卡仍传 BF16，省一半通讯？

为此加了第二个开关 `embedding_grad_fp32_local_bf16_comm`（提交 `f70d74cb`）：本卡 FP32 scatter-add，舍一次 BF16，再 BF16 跨卡 all-reduce。结果（[实验矩阵「B1h 修法②」](../alignments/04-tpu-self/MATRIX.md#b1h-修法②本地-fp32-累加跨卡仍-bf16)）：

| | 默认（全程 BF16） | `embedding_grad_fp32` | 本卡 FP32、跨卡 BF16 |
|---|---|---|---|
| 第 1 步词嵌入梯度离 FP64 | 1.51e-2 | 3.79e-3 | 4.24e-3 |
| 300 步曲线最差 r | 2.62 | 0.98 | 0.93 |
| 1000 步 | — | 1.09 | 1.07 |
| 每步每设备跨卡字节数 | 9.90e8 | 9.90e8 | 9.90e8 |

精度修好了，跨卡仍用 BF16 也够。这本身已经在暗示：跨卡那一步不是主因。

通讯量却没省下来：`embedding_grad_fp32` 下编译器把主输入、MTP 输入两路合成一次 FP32 all-reduce，字节数本来就和默认的两次 BF16 一样。

## 第七幕：审计编译产物，第一个假设被推翻

与此同时，把两种并行编出来的训练步程序逐个查了一遍：每一次梯度跨卡求和是什么数据类型、在不在累积循环里、对应哪个参数、跨卡前后各舍入几次（[B1 梯度的跨卡归约](../alignments/04-tpu-self/b1-grad-reduction.md)）。

再把第 1 步的词嵌入梯度按行分组，每组算离 FP64 的相对误差（同一文件第四节）。这里按这一行的 token 在这一步全局批里一共出现几次分组（16 条序列，主输入和 MTP 输入合计），和开头那张按「一次 scatter 里出现几次」分组的单算子表口径不同：

| 行（三组互不重叠，合起来是全部 10911 行） | 行数 | golden | 纯数据并行 8 | 纯数据并行 8、不累积 | 纯数据并行 16 |
|---|---|---|---|---|---|
| 每个微批只在 1 张卡上出现 | 7638 | 9.31e-3 | 9.41e-3 | 9.16e-3 | 9.25e-3 |
| 出现在 ≥ 2 张卡上、合计 ≤ 300 次 | 3234 | 7.77e-3 | 8.31e-3 | 8.26e-3 | 8.33e-3 |
| 合计 ≥ 301 次（高频） | 39 | 3.26e-3 | **1.57e-2** | **3.07e-2** | **1.59e-2** |

golden 是 FSDP 8；后三列每张卡一次 scatter 的下标数分别是 4096、8192、4096。高频那 39 行占整张梯度范数平方的 0.90，前两组合起来只占 0.10。

这张表推翻了第四幕的解释，也把「高频」这个条件摆了出来：

- **低频行，几种跑法几乎一样。** 前两行纯数据并行最多比 golden 远 1.07 倍（第二行 8.31e-3 对 7.77e-3）。这是本卡不排序的逐次舍入和 8 路 BF16 跨卡求和合在一起的总差；第一行的行在每个微批只出现在一张卡上，跨卡求和加的是 0，只剩本卡那一项，1.01 倍。第二行拆开要看后来的两种修法（[B1 第四节](../alignments/04-tpu-self/b1-grad-reduction.md#数据误差集中在高频-token随本卡-token-数涨)）：本卡 FP32、跨卡仍 BF16 的修法② 是 7.66e-3，全程 FP32 的修法① 是 7.28e-3，所以跨卡那一项约 1.05 倍、本卡逐次舍入约 1.09 倍，都小：这些行在一张卡上加的次数少，舍入比 scatter 之前就有的误差小。修法①（FP32 累加）的运行里，这两组是 9.31e-3、7.28e-3，和 golden 同一水平；这部分误差在 scatter 之前就有，推断来自上游的 BF16 计算，未核实。
- **差别全在 39 个高频词上。** 纯数据并行比 golden 多出来的误差，由上表按误差平方相减估算，99.6% 在这 39 行上。这样的词在一张卡、一个微批里加多少次：每个词取它出现最多的那张卡、那个微批，39 个词的中位数 74 次，最多 458 次。这是主输入和 MTP（多 token 预测）输入两次 scatter 的合计；单算主输入是 37 次、229 次（由 golden 第 1 步的 token 数出）。
- **跟本卡加的次数走，不跟跨卡的路数走。** 每卡一次 scatter 的 token 从 4096 翻到 8192，同一个高频词在这次 scatter 里加的次数也翻倍，误差实测接近翻倍（1.57e-2 → 3.07e-2）。卡数从 8 翻到 16、每卡仍 4096 个，跨卡求和的路数翻倍，误差不变（1.59e-2）。

所以主因是每张卡本地那次 BF16 scatter-add，跨卡求和是次要的。

「接近翻倍」是这一步实测到的，不是一般规律。各次舍入误差如果有正有负、互不相关，误差大约按次数的平方根涨，次数翻倍只涨约 1.4 倍。训练里接近线性，推断是舍入误差偏向一边：和越滚越大以后，后加进去的小梯度被系统性地吞掉一部分。（单算子里更新量是随机数，≥ 100 次那组从 4096 到 8192 涨了 1.26 倍；但两边不是同一批行，只作量级参考。）

这张表同时留了个反常：FSDP 那次 scatter 收的是 8 张卡的全部 token，同一个高频词在里面加的次数约是纯数据并行的 8 倍，误差反而最小。光是「加的次数多」解释不了，FSDP 那边一定有什么让它不必每加一次就舍一次。这留给第八幕。

### 两种并行的词嵌入反向，到底加什么、传什么

第七幕的反常，要落到形状上才看得清。共同部分：每张卡每个微批 1 条序列、4096 个 token；词表 E 是 [120832, 1024]；前向取行得到 X [4096, 1024]；反向传回来的 dX 是 [4096, 1024] BF16，词表的梯度 dE 由一次 scatter-add 得到：dX 的第 i 行加到 dE 的第 token[i] 行。

```
纯数据并行（每张卡存整张表）：先加后传
  卡 0：dX [4096,1024] ──scatter-add──▶ dE₀ [120832,1024] BF16    4096 个下标，不过线：不排序，加一次舍一次
  卡 1：dX [4096,1024] ──scatter-add──▶ dE₁ [120832,1024] BF16
   …                                       …
  卡 7：dX [4096,1024] ──scatter-add──▶ dE₇ [120832,1024] BF16
                         └────── BF16 all-reduce，整张表 ──────▶ dE = dE₀ + … + dE₇

FSDP（每张卡存 [120832,128]，按隐藏维切）：先传后加
  每张卡把自己的 dX 按列切成 8 段，每段 [4096,128] 送给管那 128 维的卡；token 号也收齐
  卡 k 收到：8 × [4096,128] = [32768,128] 的梯度 + 32768 个 token 号
       ──scatter-add──▶ dE[:, 128k:128k+128]   32768 个下标，过线：排序，片上 FP32 累加，只舍一次
  加完就是最终梯度，不再跨卡求和
```

两步在 golden 和纯数据并行的训练步 HLO 里都是实测看到的（每个微批主输入、MTP 输入各一组）：

| | 跨卡那一步（HLO 里的集合通信与形状） | 本卡那次 scatter-add |
|---|---|---|
| 纯数据并行 8 | 加完以后 `all-reduce`，`bf16[120832,1024]`，BF16 加法 | 输出 `bf16[120832,1024]`，没有排序 |
| FSDP 8（golden） | 加之前：token 号 `all-gather`，`s32[8,4096,1]`；梯度 `all-to-all`，`bf16[1,4096,1024]` → `bf16[1,4096,8,128]`（沿切成 8 段的那一维交换） | 先 `sort` 32768 个下标，输出 `bf16[120832,128]`，带「已排序」标记；结果直接加进 FP32 累加器，没有跨卡求和 |

按这些形状算，每张卡每次跨卡的数据量：纯数据并行一次 all-reduce 是整张表 120832 × 1024 × 2 字节 ≈ 2.47e8 字节；FSDP 一次 all-to-all 的结果是 32768 × 128 × 2 字节 ≈ 8.4e6 字节，token 号另有 1.3e5 字节。相差约 30 倍。这是按 HLO 里的形状算的，实际在线上传多少字节还取决于通信算法，没有实测。

所以同一批数，两边加法的组织完全不同：

- **纯数据并行：8 堆各自加，再把 8 个结果相加。** 每张卡在 BF16 里把自己的 4096 个更新逐次加进整张表，每加一次舍一次；然后 8 张表做 BF16 all-reduce。高频词在每一堆里都要加几十上百次。
- **FSDP：合成一大堆，排好序一次加完。** 先把 8 张卡的更新按列收齐成一堆 32768 个，下标数过了门槛，后端排序，同一个词的更新在片上 FP32 里加完，只舍一次。

「高频词 × 不排序」落在纯数据并行、没落在 FSDP，原因就在这里：FSDP 的「先传后加」让每次 scatter 的下标数翻了 8 倍，正好跨过门槛。

**矩阵乘类权重为什么两边一样。** 它们的梯度来自矩阵乘，每张卡先算出本卡的部分和（注意力投影、共享专家是 FP32；路由专家、索引器先舍成 BF16），再跨卡加。纯数据并行用 all-reduce，FSDP 用 reduce-scatter（每张卡只留自己那段）。all-reduce 等于 reduce-scatter 加 all-gather，all-gather 只搬数据不做加法，所以两边部分和的精度、跨卡加法的精度、舍入次数都相同，只差相加的先后。审计也顺带改正了一个印象：纯数据并行下以 BF16 跨卡求和的不只词嵌入，32 个 all-reduce 里有 10 个用 BF16 加法（路由专家 6 个、索引器 `wk` / `wq_b` 2 个、词嵌入 2 个）。但路由专家和索引器在 FSDP 下同样是 BF16，舍入次数相同，离 FP64 的比值（纯数据并行 ÷ golden）在 0.91–1.07，不构成差别。词嵌入不同：它的累加不是矩阵乘，是 scatter-add，FSDP 一侧换了写法。

## 第八幕：再追问，FSDP 为什么不差，纯数据并行为什么不排序

第七幕留下的反常要有个解释：FSDP 那次 scatter 也是 BF16，同一个高频词加的次数还多 8 倍，凭什么不丢精度？审计时两边 scatter 的 HLO 除了表的形状和下标个数，还看得到两处差别：FSDP 那份先按 token 号排了序，scatter 带着「下标已排序」的标记（`indices_are_sorted=true`），清零在融合内部；纯数据并行那份不排序，往融合外面传进来的零缓冲上加（[B1 第四节](../alignments/04-tpu-self/b1-grad-reduction.md#hlo-里两边的-scatter)）。后来单算子实验证明零缓冲放在哪不影响结果（[B1](../alignments/04-tpu-self/b1-grad-reduction.md)第七节的 `unsorted_buf`）。当时只能推断「排好序的 scatter 在 excess precision 下把连续的更新留在 FP32 里加」。另一个追问是：纯数据并行那份为什么不排序？

于是把这一个 scatter-add 单拿出来，在 v5p 上实测（[B1 梯度的跨卡归约](../alignments/04-tpu-self/b1-grad-reduction.md)第七节，[`emb-scatter-sort-probe-tpu.json`](../alignments/04-tpu-self/results/emb-scatter-sort-probe-tpu.json)）。表是真实形状，下标是 golden 第 1 步的真实 token，更新量是随机 BF16。结果和 CPU 上的两种仿真逐位比：一种是「FP32 里累加、最后舍一次」，一种是「每加一次舍一次 BF16」。

### 排序决定「每次舍」还是「只舍一次」

一次 4096 个下标（纯数据并行每张卡一次 scatter 的量），整张表离 FP64 的相对误差：

| | excess precision 开 | excess precision 关 |
|---|---|---|
| 不排序 | 6.75e-3，逐位等于「每次舍」 | 6.75e-3，同左 |
| 排好序、带「已排序」标记 | **1.48e-3，逐位等于「FP32 累加、舍一次」** | 6.75e-3，等于「每次舍」 |

- 只有「排序 + excess precision 开」那一格在 FP32 里累加，其余三格都是加一次舍一次。
- 排序和标记缺一不可。下标排好序但不带标记，结果仍逐位等于「每次舍」：标记是告诉后端「同一行的更新已经挨在一起」，后端见到它才换成在 FP32 里累加的那种写法。编译器自己插排序时，两样一起加。
- 开头那张按出现次数分组的表，就是左边一列这两格按行拆开。整表 6.75e-3 和 1.48e-3 之差，九成以上来自出现 10 次以上的那些行（按行范数平方与出现次数成正比估算）。

### 后端里的两种写法

两种写法的差别，在后端最终生成的机器指令里看得到（后端为一个算子生成的那段设备程序叫 kernel；[`emb-scatter-sort-aot.json`](../alignments/04-tpu-self/results/emb-scatter-sort-aot.json) 的 `llo` 部分）。拿一个在这次 scatter 里出现 3 次的词示意（token 号是随手写的）：

```
不排序：下标按 token 原来的顺序，同一个词的更新散在中间
  … 17 … 902 … 17 … 5 … 17 …
  词 17 的那一行：读 BF16 → 转 FP32 加 g1 → 舍回 BF16 → 写回
                 读 BF16 → 转 FP32 加 g2 → 舍回 BF16 → 写回
                 读 BF16 → 转 FP32 加 g3 → 舍回 BF16 → 写回      第一次加到 0 上不舍，共舍 2 次

排序后：同一个词的更新挨在一起
  … 5 … 17 17 17 … 902 …
  词 17 的那一行：在片上 FP32 缓冲里 g1 + g2 + g3 → 舍一次 BF16 → 写出   舍 1 次
```

- **不排序。** 同一个词的两次更新之间隔着别的词，后端只能每碰到一次就把那一行从 BF16 输出表里读出来、加上、舍回去。值在两次更新之间存在 BF16 的表里，excess precision 也没地方省这次舍入，所以开关不影响结果。
- **排序 + 标记。** 后端换了一颗 kernel：累加器是片上 VMEM（TPU 芯片上的高速内存）里的 FP32 缓冲，同一行的一段连续更新在里面加完，写出时才舍一次。
- **排序 + 标记，但关了 excess precision。** 同一份 HLO，这颗 kernel 多出 12288 条指令，夹在每次加法前后，又变回每次舍。训练里 FSDP 只关 excess precision，scatter 的 HLO 一字不差，高频行却远 35 倍（1.15e-1 对 3.26e-3），推断就是这个原因。

<details><summary>这一段的依据和限定</summary>

- 12288 是静态指令条数，不是执行次数。它们的作用是把值舍到 BF16，这是从指令名和「结果逐位等于每次舍」推断的。
- 后端指令是在单算子里 dump 的；训练步里是同名的 kernel，没有单独 dump。
- 35 倍出自 [B1 第四节](../alignments/04-tpu-self/b1-grad-reduction.md#数据误差集中在高频-token随本卡-token-数涨)的分组表。

</details>

一行出现 k 次，不排序要舍 k − 1 次（第一次是加到 0 上，不舍），排序只舍 1 次。k 小时差得不多（2–9 次的行 1.6 倍），k 上百时差到约 8.5 倍（1.46e-2 对 1.70e-3）：这就是「高频 × 不排序」。

### 谁来排序、什么时候排

编译器是一道道改写工序（pass）串起来的。把每道工序之后的 HLO 都存下来看，排序是 TPU 后端自己的一道工序 `tpu_scatter_gather_optimizer` 插的；它在 libtpu（TPU 的闭源编译器与运行库）里，在公开的 XLA 代码里按名字搜不到。把一次 scatter 的下标数 N 往上加，不排序那一格的误差先跟着涨，过了某个点突然掉到 FP32 累加的水平：

| 一次 scatter 的下标数 | 不排序时离 FP64（excess precision 开） | 编译器插没插排序 |
|---|---|---|
| 2048 | 4.59e-3 | 没插 |
| 4096 | 6.75e-3 | 没插 |
| 8192 | 9.14e-3 | 没插 |
| 16384 | **1.55e-3** | 插了 |
| 32768 | **1.58e-3** | 插了 |

换不同的表形状二分，门槛是**一次 scatter 的下标数超过表行数的 1/8**，和列数无关。混元 4 词表 120832 行，门槛是 15104。训练里的几种跑法：

| 运行 | 每张卡一次 scatter 的下标数 | 怎么来的 | 过线 | 排序 |
|---|---|---|---|---|
| FSDP 8（golden） | 32768 | 一个微批里 8 张卡的全部 token（8 × 4096） | 是 | 是 |
| 纯数据并行 8 | 4096 | 本卡一个微批的 token | 否 | 否 |
| 纯数据并行 16 | 4096 | 同上 | 否 | 否 |
| 纯数据并行 8，不做梯度累积 | 8192 | 一步的数据不拆微批，本卡一次 8192 个 | 否 | 否 |

门槛只认下标数，不认并行方式。FSDP 按隐藏维切，每张卡要收全部 token，下标数才过了线；反过来，纯数据并行如果每张卡一次的 token 数超过 15104，按这条规则也会被排序（推断，训练里没跑过）。FSDP 加的次数多，恰好让它走上了只舍一次的写法。

**门槛为什么在这里（推断）。** 看上去是为速度定的：更新多、同一行重复多时，先排序再在片上累加，省掉反复读写；精度更好是附带的效果。单算子耗时只部分支持这一点：排好序的写法从 4096 个下标起就更快，算上排序本身的开销，快慢交叉在 4096 到 8192 之间，和 15104 对不上。libtpu 的代码不公开，没法确认。

### 回头看 10 月的建议

10 月在测试模型上的建议之一是关掉 excess precision。当时的依据：excess precision 开着时，v5p 上 FSDP 前约 100 步一边倒偏低约 −7.9e-4；加 rng 开关并关掉 excess precision 后，v5p 上 FSDP − DDP 各段都在噪声范围内。那条评论里「回到 0 附近」说的是梯度累积下把 ZeRO-1 那条路径改成 FP32，不是关 excess precision。放到混元 4 上看，这条路走不通：纯数据并行那次 scatter 本来就是每次舍，开关管不着它；FSDP 那次排好序的 scatter 却会从「只舍一次」退回「每次舍」，而且一次要顺序加 32768 个更新。结果 FSDP 比纯数据并行还差得多：v5p 上第 1 步词嵌入梯度离 FP64 1.09e-1（纯数据并行 1.51e-2，FSDP 默认 4.00e-3），300 步 r 13.3（[影响逐件「关掉编译器的省舍入」](../alignments/04-tpu-self/impacts/02-excess-precision.md)）。测试模型上关掉它为什么能消掉那 −7.9e-4，没查：测试模型上没有逐张量对 FP64，也没看它的词嵌入 scatter 排不排序。

## 第九幕：结论和做法

**原因：高频词 × 不排序。** 两个条件缺一个都不丢精度，训练里的实测见开头的 2×2。

- 高频行差的 4.8 倍里，「排序」和「FSDP」是绑在一起的（FSDP 还少一次跨卡求和）。单算子 8 卡那组把排序单独拿了出来：纯数据并行 7.17e-3，只加上排序就到 2.86e-3，FSDP 1.58e-3（[B1 第七节](../alignments/04-tpu-self/b1-grad-reduction.md#8-个设备上照两种切法各跑一份n-每张卡-4096全局-32768)）。从 7.17e-3 到 1.58e-3 的差距，排序一项走了约八成；剩下的在本卡部分和先舍一次 BF16、再做 BF16 跨卡求和。
- 低频行写「不明显」，是训练里看不出来：单算子里出现 2–9 次的行，不排序也比排序远 1.6 倍，但训练里这些行 scatter 之前就有约 7e-3–9e-3 的误差，把这点差别盖住了。

这也解释了第二幕那张表：不做梯度累积时每卡一次 scatter 8192 个，仍不过线，同一个词加的次数翻倍，所以最差（r 3.69）；16 卡每卡仍 4096 个，和 8 卡差不多（r 2.65 对 2.62）。v7x 第 1 步同样是词嵌入梯度变远（1.50e-2 对 v7x FSDP 的 4.25e-3，R 3.54），曲线 r 2.21 本身没超过 GPU 重跑的最大值 2.47。v7x 纯数据并行那次 scatter 在 HLO 里和 v5p 一样，是不排序的 `scatter_fusion`；不同的是 v7x 的 FSDP：那次排好序的 scatter 交给了 SparseCore（`scatter_offload_custom_fusion`，[影响逐件「关掉编译器的省舍入」](../alignments/04-tpu-self/impacts/02-excess-precision.md)）。两边在 v7x 后端里各按什么精度累加没单独实测，是推断。

**GPU 为什么没有这个问题。** GPU 上同样设置的词嵌入梯度离 FP64 4.17e-3，和 TPU FSDP 的 4.00e-3 接近。PyTorch 在 CUDA 上的词嵌入反向（[`aten/src/ATen/native/cuda/Embedding.cu`](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/Embedding.cu) 的 `embedding_dense_backward_cuda`，和 [`EmbeddingBackwardKernel.cu`](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cuda/EmbeddingBackwardKernel.cu)）按下标数分两条路：

| 一次的下标数 | 写法 | 同一个词的累加 |
|---|---|---|
| ≤ 3072 | `embedding_backward_feature_kernel`：每次装 32 个下标，同一行的在共享内存里用 `accscalar_t`（BF16 输入时是 float）加起来，再加回 BF16 的输出 | 每 32 个下标一批在 FP32 里加，批与批之间舍一次 BF16 |
| > 3072 | 先 `radix_sort_pairs` 把下标排好序，按段在 `acc_type`（float）里累加；融合版用 FP32 的中间缓冲做原子加，最后才转回 BF16 | 全在 FP32 里，最后舍一次 |

混元 4 的 GPU 运行本身就是数据并行 8，每卡每个微批也是 4096 个 token（[协议](../PROTOCOL.md)「序列 / 批」一行），超过 3072，推断走的是第二条路：和纯数据并行同样的切法，本卡累加却和 TPU FSDP 排序后的写法是同一种舍入结构。第一条路也比 TPU 不排序的写法好：同一行的更新先在 FP32 里成批合并，不是每加一次舍一次。读的是 PyTorch 主分支；GPU 镜像里那个 PyTorch 版本的这两条路没有逐行核过，GPU 运行实际走了哪条也没有单独确认。

**修法为什么有效。** 两种修法都绕开了「高频行在 BF16 里加一次舍一次」：

- ① `embedding_grad_fp32`：整次 scatter 和跨卡求和都在 FP32 里做。单算子里 FP32 scatter 离 FP64 只有 2.6e-9，比 BF16 小六个数量级，加几百次也看不出来。
- ② `embedding_grad_fp32_local_bf16_comm`：本卡在 FP32 里加完，每行只舍一次 BF16，再用 BF16 跨卡求和。本卡这一段和 FSDP 排序后的写法一样只舍一次，比 FSDP 多出一次 8 路 BF16 跨卡求和。训练里这一项只让误差从 3.79e-3（修法①）变成 4.24e-3，300 步 r 0.93，在噪声内。

**修法**（[影响逐件「纯数据并行」](../alignments/04-tpu-self/impacts/01-data-parallel.md)）：

| 修法 | 第 1 步词嵌入梯度离 FP64 | 曲线最差 r | 步时（对 golden，按芯片·秒） |
|---|---|---|---|
| 不修 | 1.51e-2 | 2.62 | −3.4% |
| ① `embedding_grad_fp32`（`d5c9b113` 之后） | 3.79e-3 | 300 步 0.98，1000 步 1.09 | −2.8% |
| ② `embedding_grad_fp32_local_bf16_comm`（`f70d74cb`） | 4.24e-3 | 300 步 0.93，1000 步 1.07 | −2.6% |

步时一列是相对 golden 的变化，负数表示比 golden 快；修法本身多 0.6–0.8 个百分点，跨卡字节数不变。

**换到别的模型怎么自查。** 用来判断没开修法的跑法有没有中招。看每张卡一次词嵌入 scatter 的下标数 N 和词表行数 V。N 在纯数据并行下是本卡一个微批的 token 数；在词表按隐藏维切的 FSDP 下，是切分组里所有卡一个微批的 token 数。主输入、MTP 输入分开算。

| 情况 | 会怎样 | 做法 |
|---|---|---|
| N ≤ V / 8 | 不排序，高频词丢精度 | 开修法①或② |
| N > V / 8 | 后端自动排序，只舍一次（excess precision 开时；v5p 实测） | 不修也行；开修法在混元 4 mini 上多 0.6–0.8 个百分点 |

按这条规则，FSDP 如果一个微批的 token 太少，也会落到不排序那一边（推断，没跑过）。门槛 V / 8 是在当前这个 libtpu 构建上二分出来的，换版本可能变；表很小时（30000 × 128 的表到 65536 个下标都不插排序）也不插。所以最稳的做法是不靠门槛，直接开修法①。

## 第十幕：经验

- **第 1 步对 FP64 逐张量定责，一步把范围从整个模型缩到一个张量。** 曲线只能说有偏差，说不出偏差在谁身上。
- **一个张量里也要按行分组看。** 整张表的误差被 39 个高频行主导；按「这一行加了几次」分组，「高频」这个条件才浮出来，也才看得出 FSDP 加得更多却更准这个反常。
- **第一个解释被推翻，第二个解释要实测才算数。** 先以为是跨卡求和，按行分组后发现是本卡累加；「排好序的 scatter 留在 FP32」一开始只是推断，单算子实测才坐实，还发现起作用的是标记，触发条件是下标数。
- **「为什么 FSDP 不差」这类追问不能停在 HLO 上。** HLO 一字不差的两次运行，后端生成的指令可以完全不同。
- **精度可以随批大小变。** 同一份代码，每张卡一次 scatter 的 token 数过不过门槛，走的是两种写法。换批大小、换卡数、换切法，都要重新看。
- **编译器 bug 只在特定组合出现。** 数据并行、梯度累积、开关三者同时成立才丢梯度。修法上线前要按组合跑，不能只跑默认配置。
- **「让两边一样」不等于「让两边都对」。** 关 excess precision 在测试模型上被用来消 FSDP 前约 100 步的偏低（10-16 评论，单次运行；为什么能消，没查），在混元 4 上却让 FSDP 的词嵌入梯度离 FP64 远到 golden 的 27 倍（1.09e-1 对 4.00e-3；按定责用的 R，分母取 max(golden, GPU 4.17e-3)，是 26.1）。修法要看离精确值近不近，不能只看两边的差。
- **每个修法都要回头核默认路径。** 两次 MaxText 改动后，golden 重跑都逐位相同。

## 第二阶段：只把词嵌入表沿数据并行轴切开


前十幕 查清了纯数据并行（DDP）下词嵌入梯度丢精度的原因：每张卡先在本卡把 4096 个 token 的梯度 scatter-add 进整张 BF16 表，下标数没到后端插排序的门槛，高频词每加一次舍一次；FSDP 下同一个 scatter 收齐 8 张卡的 token、排好序、在片上 FP32 里加完只舍一次。第一版修法让 DDP 的那次累加改在 FP32 里做，精度修好了。

这一阶段换了个做法：其余参数仍是纯数据并行，**只把词嵌入表一个参数沿数据并行轴切开**，让编译器对它自动生成 FSDP 那条路径。下面按顺序写：第一版之后还剩什么问题、为什么想到照 FSDP 的方式做、新切分怎么设计、怎么从编译产物看通信、上卡验证、结论。


### 第一版之后还剩什么问题

第一版有两个开关（[案例 14 第九幕](#第九幕结论和做法)）：`embedding_grad_fp32`（本卡累加和跨卡求和都在 FP32）和 `embedding_grad_fp32_local_bf16_comm`（本卡 FP32 累加，跨卡仍 BF16）。两者都把精度修回了噪声内，但都没动 DDP 处理词嵌入梯度的结构：

- **每张卡仍然对整张表求和。** 一个微批里每张卡只有 4096 个 token，整张表 120832 行里最多 4096 行有梯度，跨卡求和传的却是整张表。三种 DDP 跑法（不修、修法①、修法②）的训练步程序里，词嵌入梯度的跨卡求和每步每设备都是 9.90e8 字节，占 DDP 全部集合通信（2.70e9）的 37%（下文[对比表](#五种跑法的对比)）。
- **修法①没有让字节翻倍，但原因是巧合。** 修法①的 all-reduce 是 FP32，每个元素 4 字节；编译器把主输入和 MTP 两路的 scatter 合成一次，每个微批只做 1 次 FP32 all-reduce，而默认是每个微批 2 次 BF16。两边都在梯度累积循环里，每步分别是 2 次和 4 次，字节数相同。只有一路输入的模型，FP32 那份就是两倍（推断）。另外修法①的程序里，词嵌入那次 scatter 之前多了 8 次 `collective-permute`（把部分 token 的梯度和 id 换到别的卡），每步 6.7e7 字节，总通信比默认多 2.7%。
- **每张卡存整张表和它的优化器状态。** FP32 主权重加两份 Adam 动量，每张卡 120832 × 1024 × 4 × 3 ≈ 1.48e9 字节，8 张卡存了 8 份一样的。
- **修法①依赖一个绕编译器 bug 的屏障。** 整表 FP32 累加器在梯度累积循环里，编译器曾把它的 all-reduce 挪出循环、每次迭代把 0 号以外的累加器清零（案例 14 第五幕），现在靠每个微批一个 `optimization_barrier` 挡住。

### 换个角度：为什么不照 FSDP 的方式做

DDP 的 all-reduce 等于 reduce-scatter 加 all-gather。词嵌入梯度在 DDP 下是「先加后传」：每张卡先把本卡的 token 梯度乱序加进整张表，再跨卡求和。FSDP 下是「先传后加」：每张卡把未累加的原始 token 梯度按列切成 8 段，送到管那一段的卡上，那张卡收齐 8 张卡的全部 token（32768 个），排好序在 FP32 里一次加完（[案例 14「加什么、传什么」](#两种并行的词嵌入反向到底加什么传什么)）。

FSDP 这条路径不是谁手写的，是编译器在「表按隐藏维切开」这个前提下自动切分出来的。所以不需要新写 kernel，只要让 DDP 下的词嵌入表也切开就行：

- **精度。** 每张卡那次 scatter 收 32768 个下标，过了排序门槛（15104），病根「高频词 × 不排序」不再成立（预期）。
- **反向通信。** 原来每个微批每路输入对整张表 all-reduce 一次（2.47e8 字节）；改成交换 token 梯度，每卡每次 4096 × 1024 × 2 ≈ 8.4e6 字节，外加 token id（预期）。
- **all-gather 不会消失，只是换了位置。** 表切开后优化器只更新本卡那 1/8，反向末尾不再需要把整张表的梯度拼回每张卡；代价是前向开头要从别的卡取表。编译器可能把整张表 all-gather 过来，也可能像 FSDP 反向那样只交换 token id 和那几千行向量（编译前不知道，要看编译产物）。

要防的坑有两个：开重算时，前向的这些通信可能在反向里再来一遍；传过去的必须是未累加的原始 token 梯度，不能是本卡先加好的整表。

### 新切分的设计

MaxText 开关 `embedding_shard_over_data`（默认关；maxtext 混元 4 集成分支，提交 `9099c8ce`）：

- **只改词嵌入表。** 表的形状是 [词表, 隐藏维]，原来的逻辑轴是 `("vocab", "embed_vocab")`；开关打开时隐藏维换成新的逻辑轴 `embed_vocab_table`。和 FSDP 一样切隐藏维。
- **单独起一个逻辑名。** `embed_vocab` 不能直接加 `data`：输出头的 kernel（[隐藏维, 词表]）也用它，加了就把输出头一起切了。新名字的映射规则由配置在开关打开时追加：`data` 加上 `embed_vocab` 原来的那些轴（`fsdp`、`fsdp_transpose`、`context`、`context_usp_ulysses`、`expert`），所以在数据并行 × FSDP 混合时，表沿两个轴一起切。自定义规则文件不用改。激活值用的 `embed` 等逻辑轴不受影响。
- **MTP 一起生效。** MTP 层取输入用的是同一张表（`shared_embedding` 就是主模型的 `token_embedder`），编译产物里主输入和 MTP 各一组通信（见下）。
- **开关关着时程序不变。** Embed 的逻辑轴和规则表都和原来一样。离线编译核对：FSDP 8 和 DDP 8 两种配置，本提交与基底 `f76a136f` 编出的训练步程序去掉元数据后逐字相同。
- **和 ZeRO-1（`shard_optimizer_over_data`）互斥**，配置检查直接拒绝：ZeRO-1 会再往优化器状态上加一次 `data`。
- 单测 `tests/unit/embedding_shard_over_data_test.py`（CPU 8 设备）：开关关着不加规则、打开时规则是 `data` 加 `embed_vocab` 的轴；参数的逻辑轴；两种切分下梯度都等于 scatter-add；关着时有整表的 all-reduce，打开后没有。

### 怎么从编译产物看通信

上卡之前，先在 CPU 上把训练步按目标拓扑编一遍，从编译出来的程序里把每一次集合通信找出来。这一节写这套方法，后面的对比表都是这样得到的。

#### 为什么能离线看

XLA 编译不需要芯片在场：MaxText 的 `train_compile` 能拿到一个目标拓扑（例如 `v5p-16`，8 片 v5p、8 个 JAX 设备）的描述，在 CPU 上为它做完整的切分和后端编译，产物和上卡时编的是同一个程序。混元 4 mini 一次编译约 85–120 秒，进程峰值内存约 15 GiB，不占卡。

这一阶段编了 9 份：DDP 8、FSDP 8（基底与本提交各一份）、DDP 8 + `embedding_grad_fp32`、DDP 8 + `local_bf16_comm`、DDP 8 + `embedding_shard_over_data`，另有重算 `full` 的两份。上卡后把 TPU 上存下的训练步程序拿来比，集合通信逐条一致（DDP 8 + 新开关：39 条、每步总字节相同；离线与在线的差别只在 `replica_groups` 的写法），所以下面的表直接用各运行目录里上卡时存下的程序。

#### 怎么编、看哪个文件

和 TPU 上训练用同一套配置（对齐 yml、阶段覆盖、命令行覆盖）、同一个训练步 jit，只把设备换成拓扑描述、把训练状态和 batch 换成同形状同切分的抽象值。编译时让 XLA 把训练步模块的 HLO 存成文本：

```bash
# 在 MaxText 训练镜像里（镜像 digest 见 frameworks/maxtext/run.sh），CPU 上
JAX_PLATFORMS=cpu ALLOW_MULTIPLE_LIBTPU_LOAD=1 TPU_SKIP_MDS_QUERY=1 \
HY4_YML=models/hunyuan4/frameworks/maxtext/hy4-mini-t1.yml \
XLA_FLAGS="--xla_dump_to=<目录>/xla --xla_dump_hlo_as_text --xla_dump_hlo_module_re=.*train_step.*" \
  python models/hunyuan4/frameworks/maxtext/aot_hlo.py --stage mini --topology v5p-16 --steps 300 --out <目录> \
    ici_data_parallelism=8 ici_fsdp_parallelism=1 embedding_shard_over_data=true
```

`<目录>/xla/` 下每个模块有一串文件。只看 `*.jit_train_step.*.after_optimizations.txt`：这是切分、融合、调度都做完以后的程序，里面的集合通信就是上卡时要执行的那些。`before_optimizations` 那份还没切分，看不到通信。上卡运行加 `XLA_DUMP=1` 时，同一份文件拷在运行目录的 `hlo/train_step.after_optimizations.txt`。

#### 认出集合通信

每条指令一行，形如 `%名字 = 结果形状 操作(操作数), 属性…`。五种集合通信：

| 操作 | 长什么样 | 含义 |
|---|---|---|
| `all-reduce` | `%all-reduce.1131 = f32[1024,120832]{…} all-reduce(%x), replica_groups=…, to_apply=%add…` | 各卡同形状的数逐元素相加，结果每张卡一份。`to_apply` 指向的计算是加法；结果的数据类型就是相加用的类型。多个张量合成一次时结果是元组 |
| `all-gather` | `%all-gather.23 = s32[8,4096,1]{…} all-gather(%x), dimensions={0}` | 沿 `dimensions` 那一维把各卡的切片拼起来，结果比输入大 8 倍 |
| `all-to-all` | `%all-to-all.23 = bf16[1,4096,8,128]{…} all-to-all(%x), dimensions={2}` | 沿 `dimensions` 那一维切成 8 份，第 i 份送给第 i 张卡；形状不变 |
| `collective-permute` | `%collective-permute-start.4 = (bf16[1,4096,1024], bf16[1,4096,1024], u32[], u32[]) collective-permute-start(%x), source_target_pairs={{1,0},{2,1},…}` | 按 `source_target_pairs` 点对点发送；异步版的结果是（发送缓冲, 接收缓冲, 两个上下文）的元组 |
| `reduce-scatter` | `… reduce-scatter(%x), dimensions={…}` | 先求和、每张卡只留一段。这次的五份程序里没有出现 |

异步的写法是 `xxx-start` / `xxx-done` 成对出现，算一次。

#### 认出它属于哪个参数

两种办法，结论要对得上：

- **按形状。** 词嵌入表是 [120832, 1024]，切开后是 [120832, 128]；输出头的 kernel 是 [1024, 120832]，第一维不同。token 相关的形状带 4096（每卡一条序列）或 32768（8 卡的 token 收齐）。
- **按 metadata。** 每条指令带 `metadata={op_name="…"}`，是 JAX 里产生它的算子名：`jvp()/gather` 是前向取行，`transpose(jvp())/scatter-add` 是反向往表里加，`jvp()/select_n` 是 token id 的越界裁剪（id 的 all-gather 就挂在它后面）。

形状和名字都不够确定时，顺着数据流看它的使用者：例如 DDP 8 + 新开关里有 4 条 `s32[8,4096,1]` 的 all-gather，两条的使用者是前向那次 gather 前的裁剪，另两条进了 `sort`、再进带排序标记的 scatter。

#### 在不在循环里，每步执行几次

程序由若干计算（computation）组成，`while(…), condition=%c, body=%b` 表示循环。梯度累积是最外层的一个循环，层扫描、窗口化矩阵乘是里面的循环。优化后的 HLO 不写循环次数，要从条件计算里读：它的 ROOT 是 `compare(计数器, %常数), direction=LT`，那个常数就是循环次数（例如梯度累积那一层是 2）。一条通信每步执行的次数，是从 ENTRY 到它所在计算这一路上各个循环次数的乘积。

例：DDP 8 里词嵌入梯度的 all-reduce 有 2 条（主输入、MTP 输入各一条），都在梯度累积循环体里，每步各执行 2 次，共 4 次。

#### 字节怎么算

每步每设备字节 = 结果形状的元素数 × 字节宽（BF16 2、FP32 4、S32 4）× 每步次数。all-reduce 算被求和的那块，all-gather 算拼好后的结果，all-to-all 算交换的那块，异步 collective-permute 只算元组里的一块缓冲。例：`bf16[120832,1024]` 是 2.47e8 字节，每步 4 次是 9.90e8。

脚本 [`analysis/hlo_comm_bytes.py`](../analysis/hlo_comm_bytes.py) 做上面这几步：列出每条集合通信，按（类型, 形状）合并，给出每步次数、每步字节和一个 op_name 样本：

```bash
python models/hunyuan4/analysis/hlo_comm_bytes.py \
  ddp8=<ts-dp8>/hlo/train_step.after_optimizations.txt \
  ddp8-shard=<ts-esd-dp8>/hlo/train_step.after_optimizations.txt --out comm.json
```

哪几行属于词嵌入，脚本不替你判断，按上一小节认。

#### 认出 scatter 排没排序

找结果形状是表（或表的切片）的 `scatter(…)`。带排序的写法有两个标志，缺一不可（案例 14 第八幕）：

- scatter 前面有一个 `sort`，对 token id（例如 `s32[32768]`）连同一个 `iota` 一起排序，scatter 用的是排好的 id；
- scatter 的属性里有 `indices_are_sorted=true`。

DDP 8 那次 scatter 结果是 `bf16[120832,1024]`，没有 sort，也没有这个标记；FSDP 8 和 DDP 8 + 新开关的 scatter 结果是 `bf16[120832,128]`，前面是 32768 个 id 的 `sort`，带 `indices_are_sorted=true`。

#### 五种跑法的对比

数据来自各运行上卡时存下的训练步程序（运行目录 `hlo/`），由 `hlo_comm_bytes.py` 算出（[`emb-shard-over-data-comm.json`](../alignments/04-tpu-self/results/emb-shard-over-data-comm.json)）。都是 v5p 8 设备、每设备微批 1 × 梯度累积 2，每步执行次数已乘上循环次数。

| | DDP 8 | DDP 8 + `embedding_grad_fp32` | DDP 8 + `local_bf16_comm` | FSDP 8（golden） | DDP 8 + `embedding_shard_over_data` |
|---|---|---|---|---|---|
| 运行 | `ts-dp8` | `ts-fx-dp8-embf32` | `ts-ebc-dp8` | `ts-fx-g`（与 golden 逐位相同） | `ts-esd-dp8` |
| 词嵌入的前向通信 | 无 | 无 | 无 | id `all-gather s32[8,4096,1]` 每步 4 次；取到的行 `all-to-all bf16[8,1,4096,128]` 每步 4 次 | 同 FSDP 8 |
| 词嵌入的反向通信 | `all-reduce bf16[120832,1024]` 每步 4 次 | `all-reduce f32[120832,1024]` 每步 2 次（两路合成一次）；scatter 前 `collective-permute bf16[1,4096,1024]` 8 次、`s32[1,4096,1]` 8 次 | `all-reduce bf16[120832,1024]` 每步 4 次 | id `all-gather` 每步 4 次；token 梯度 `all-to-all bf16[1,4096,8,128]` 每步 4 次 | 同 FSDP 8 |
| 本卡 scatter | `bf16[120832,1024]`，不排序 | `f32[120832,1024]`，不排序 | `f32[120832,1024]`，不排序 | `bf16[120832,128]`，排序 | `bf16[120832,128]`，排序 |
| 词嵌入通信，每步每设备字节 | 9.90e8 | 1.06e9 | 9.90e8 | 6.82e7 | 6.82e7 |
| 全部集合通信，每步每设备字节 | 2.70e9 | 2.77e9 | 2.70e9 | 1.32e10 | 1.78e9 |
| 参数与优化器状态，每设备（离线编译的 argument size） | 4.41e9 | 4.41e9 | 4.41e9 | 5.59e8 | 3.12e9 |
| 实测显存峰值，每设备 | 6.16e9 | 6.16e9 | 6.16e9 | 1.82e9 | 4.46e9 |

- DDP 8 + 新开关的词嵌入通信和 FSDP 8 一条不差：同样 4 条 id 的 all-gather、4 条 all-to-all，同样一次带排序的 scatter。词嵌入的通信从 9.90e8 降到 6.82e7，少了 93%；全部集合通信从 2.70e9 降到 1.78e9，少了 34%。
- 前向没有整表的 all-gather。前向的做法和 FSDP 反向对称：先收齐 8 张卡的 token id，每张卡从自己那 128 列里取出 32768 个 token 的行，再用 all-to-all 换回每张卡自己那 4096 个 token 的整行。
- FSDP 8 的全部通信大，是因为其余参数也都切开了（每个微批前向、反向都要收齐权重），和词嵌入无关。
- 参数与优化器状态少 1.30e9 字节，就是词嵌入表的 FP32 主权重和两份动量从整份变成 1/8（1.48e9 × 7/8）。

#### 重算有没有把通信再做一遍

没有。词嵌入在层扫描之外，不在重算范围里：现行配置（`custom`）下前向的 all-to-all 每路输入每个微批只有 1 次。重算策略改成 `full` 再编一遍，词嵌入的通信条数、每步次数、字节都不变（每步总字节仍是 1.78e9）。

要说明的一点：token id 的 all-gather 前向、反向各做了一次（每路输入每个微批 2 次），反向没有复用前向收齐的 id。这和重算无关，FSDP 8 的程序里也是这样；每次 1.3e5 字节，可以忽略。

#### 这套方法的边界

- 字节是按 HLO 里的形状算的，不是线上实测。实际传多少还取决于通信算法：例如 ring all-reduce 每设备约收发 2(n−1)/n 倍的数据，all-to-all 约 (n−1)/n 倍。表里的数只适合互相比。
- 看得到「传什么、传几次、在哪做排序」，看不到数值精度：后端对同一条 HLO 可以生成完全不同的指令（案例 14 第八幕关 excess precision 的例子）。精度要上卡做第 1 步逐张量定责。
- 看不到快慢：通信能不能和计算重叠，要看实测步时或 profile。

### 结论

**只把词嵌入表沿数据并行轴切开，就修好了纯数据并行下的词嵌入梯度，而且不用为精度付通信。**

- **机理如预期。** 编译器对这一个参数生成了和 FSDP 一样的「先传后加」：反向交换的是未累加的原始 token 梯度（每次 8.4e6 字节），每张卡对 32768 个 id 排序后做一次带 `indices_are_sorted=true` 的 scatter。病根「高频词 × 不排序」不再成立。
- **前向是对称的，没有取整表。** 前向收齐 token id，各卡从自己那 1/8 列取行，再 all-to-all 换回整行。原来 all-reduce 里「all-gather 那一半」变成了这次前向的 all-to-all。
- **重算没有重复这些通信**（现行 `custom` 和 `full` 都核过）。token id 的 all-gather 前向、反向各做一次，FSDP 也是这样，字节可以忽略。
- **精度和前两种修法一样。** 第 1 步词嵌入梯度离 FP64 3.97e-3（FSDP 4.00e-3），205 个张量没有丢精度的；300 步 r 1.02、1000 步 1.15，都和 GPU 重跑分不开。
- **代价是负的。** 词嵌入的通信每步每设备 9.90e8 → 6.82e7 字节（按形状算），全部集合通信少 34%；显存峰值少 1.70e9 字节；步时和不修一样，比修法①②快 0.4–0.7 个百分点。

和前两种修法比，它不靠 FP32、不靠绕编译器 bug 的屏障，换的是切分方式本身。仍要注意两点：

- 它依赖每张卡那次 scatter 的下标数过排序门槛（表行数的 1/8）。这里每卡 32768 个，是门槛的两倍多；数据并行路数或每卡 token 数小到 8 张卡合起来也不过线时，会退回不排序（推断，没跑过），这时仍要用修法①。
- 只在 v5p、hy4-mini、DDP 8 + 累积 2 上验证过；v7x、生产尺寸、数据并行 × FSDP 混合时没跑。
