# 纯数据并行：词嵌入梯度丢精度

从现象到后端指令的完整排查经过，见[案例 14](../../../cases/14-ddp-fsdp-embedding.md)。

## 改了什么

golden 用 FSDP 8：每张卡只存八分之一的权重，用到时再从别的卡收齐。纯数据并行是每张卡存一整份权重，各算各的数据，最后把八张卡的梯度加起来。两种做法数学上等价，一次实际排查比的就是这两种。

## 影响多大

8 卡、每步两个微批（和 golden 一样）时，曲线最差的一项是梯度范数的带符号均值，r 2.62，判「超」。

方向是固定的：TPU 的主 loss 一直偏高（带符号均值 +5.58e-6），梯度范数一直偏低（−2.60e-4）。

换别的条件也一样：

| 条件 | 曲线最差 r |
|---|---|
| 8 卡，每步两个微批 | 2.62 |
| 8 卡，不做梯度累积 | 3.69 |
| 16 卡 | 2.65 |
| v7x，8 个设备 | 2.21 |
| v7x，8 个设备，不做梯度累积 | 4.06 |

以上都是 libtpu 0.0.46。在这个版本上，问题和卡数、芯片代际无关。换到 libtpu 0.0.52，v7x 上不做梯度累积的那一行变了，见下面「换 libtpu 版本」。五种条件都判「超」（r > 2）；其中 v7x 的 2.21 没超过 GPU 自己重跑能到的最大值 2.47（留一法），单看曲线和 GPU 重跑分不开，是第 1 步词嵌入梯度 R 3.54 把它分开的。

## 问题出在哪

第 1 步 205 个参数梯度里，只有词嵌入梯度变差：离 FP64 1.51e-2，GPU 是 4.17e-3，golden 是 4.00e-3。按定责的 R（分母取两者里较远的 GPU）是 3.62；只对 golden 比是 3.77 倍。

其余 204 个和 FSDP 一样近（离 FP64 的比值中位数 0.99）。

## 为什么

词嵌入的反向是 scatter-add：每个 token 把自己的梯度加回词表里自己那一行。它不是矩阵乘，累加的精度跟着表的类型走。

原代码先把整张表转成 BF16 再取行，反向就在 BF16 里加。BF16 一次舍入的相对误差是 2^-8 ≈ 3.9e-3 这个量级；高频词在一张卡上一个微批里要加几十到几百次（这 39 个高频词，每个取出现最多的那张卡、那个微批：中位数 74 次，最多 458 次。这是主输入和 MTP 输入两次 scatter 的合计；单算主输入是 37 次、229 次），后面加进去的小数会被吞掉。

### 同样是把所有 token 的贡献加起来，为什么 DP 差、FSDP 不差

**加的是同一批数。** 数学上，词表每一行最后加进去的项，两边是同一批：这一行对应的 token 在全局批里的每一次出现。差别只在怎么加、每加一次舍入到什么精度。

**FSDP 怎么加。** 词表按列切，每张卡负责自己那 128 列，要用到全局批全部 32768 个 token 在这几列上的梯度：先把 8 张卡的 token 编号收齐，再把这几列上的梯度换到本卡，一次 scatter-add 加完。词嵌入梯度没有跨卡求和。

编译器在这次 scatter 前面插了排序，并把 scatter 标成「下标已排序」（`indices_are_sorted=true`）。插排序的是 TPU 后端的 pass `tpu_scatter_gather_optimizer`，在 libtpu 0.0.46 上二分，条件是一次 scatter 的下标个数超过词表行数的 1/8（严格大于；120832 行即超过 15104 个），7 种表形状全部吻合；这条规律对 v5p 的各种列宽、v7x 上列数 1024 的表成立，v7x 上列数 128 的表交给 SparseCore 执行，下标数到 2 就排序，另算；前提是整张表按 FP32 放不进片上内存。更新的 libtpu 门槛会随列宽和芯片代际变化，换版本要重测，或者直接看 HLO 里有没有 `sort` 和 `indices_are_sorted=true`。在 libtpu 0.0.52 上离线编译实测：列数 1024 的表 v5p 门槛 14420、v7x 7181，列数 128 的表 v5p 1783（[`libtpu-052.md`](../libtpu-052.md#词嵌入那次-scatter排不排序)）。FSDP 每张卡收的是 32768 个，两个版本都过线；这和切分方式本身无关。

标了「已排序」，TPU 后端就换一种写法：表按块搬进片上 FP32 缓冲，块内所有更新加完再写回，每行只舍一次；下标有序时块才能顺序推进（LLO 实验确认）。前提是 excess precision 开着；关掉后同样的程序每加一次就舍一次，这就是「只关 excess precision，scatter 的 HLO 一字不差，高频行却远 35 倍」。这层在 HLO 里看不到，单算子实验在后端代码里看到了，结果逐位对上「FP32 累加、舍一次」的仿真。

**DP 怎么加。** 每张卡先对自己那 4096 个 token、对整张表做 scatter-add。4096 不到 15104（libtpu 0.0.46 的门槛），编译器不排序；后端对每个更新都把那一行 BF16 读出来、加上、舍回 BF16 写回，每加一次舍一次，每次是 2^-8 这个量级。单算子实验里这一种开不开 excess precision 都逐位等于「每加一次舍一次」的仿真。然后每个微批再做 8 路 BF16 all-reduce（主输入、MTP 输入各一次），把八张卡的结果加起来。

**跨卡那一步为什么不是主因。** all-reduce 可以看成 reduce-scatter 加 all-gather。all-gather 只搬数据，不产生误差；reduce-scatter 每个元素只加 8 个数，按树形加是 3 层，按顺序加也只有 7 次加法（具体怎么加 HLO 里看不到）。和本卡那几十到几百次舍入比，量级小得多。实测拿修法②（本卡 FP32、只舍一次，跨卡仍是 BF16）对修法①（全程 FP32）：跨卡那次 BF16 求和让高频行从 3.08e-3 到 3.60e-3（1.17 倍），出现 ≤ 300 次、在多张卡上的行从 7.28e-3 到 7.66e-3（1.05 倍）；不排序的本卡累加让高频行从 3.60e-3 到 1.57e-2（4.4 倍）。所以主因不是「两边求和的顺序不同」，而是「舍入发生了多少次、每次舍多少」。

**证据**（第 1 步词嵌入梯度按行分组，算离 FP64 的距离）：

| 看什么 | 结果 |
|---|---|
| 误差在哪些行 | 多出来的误差几乎全在 39 个高频词的行上，这些行占梯度范数平方的 0.90 |
| 每张卡一次 scatter 的 token 数翻倍 | 4096 个时高频行 1.57e-2，8192 个时 3.07e-2，跟着翻倍。所以不做梯度累积更差 |
| 卡数翻倍（每卡仍是 4096 个） | 8 卡 1.57e-2，16 卡 1.59e-2，几乎不变 |
| 每个微批只在一张卡上出现的行 | 不经过跨卡相加（BF16 all-reduce 加的是 0），这些行和 FSDP 一样：9.41e-3 对 9.31e-3 |
| 出现 ≤ 300 次、在多张卡上的行 | 纯数据并行只比 golden 远 1.07 倍（8.31e-3 对 7.77e-3）。这是本卡逐次舍入和 8 路 BF16 all-reduce 合在一起的总差；拿修法②、修法①拆开，跨卡那一项约 1.05 倍、本卡那一项约 1.09 倍 |

**FP32 为什么能修。** 加的顺序照样和 FSDP 不同，但每次加法的舍入从 2^-8 量级降到 2^-24 量级，小了 2^16 = 65536 倍。估算：最高频的词在一张卡上加 458 次，按 FP32 每次 2^-24 线性累加也只有约 2.7e-5，仍远小于一次 BF16 舍入的 3.9e-3，所以看不出来。实测修后词嵌入梯度离 FP64 3.79e-3，比 golden 的 4.00e-3 还近。

按行分组的数据在 [`emb-grad-row-groups.json`](../results/emb-grad-row-groups.json)。逐个 all-reduce 的数据类型和舍入次数见 [B1 梯度的跨卡归约](../b1-grad-reduction.md)第一至四节；单算子实验（四格、随下标个数的变化、插排序的门槛、后端代码）见同一页第七节。

## 换 libtpu 版本

在 libtpu 0.0.52 上重测（V 类，对 0.0.52 的 golden `ts-g52-a` 比；[`libtpu-052.md`](../libtpu-052.md)）：

| 跑法 | 0.0.46 | 0.0.52 |
|---|---|---|
| v5p 8 卡，每步两个微批，不修 | 超，r 2.62，词嵌入梯度 R 3.62 | 超，r 2.82，R 3.60 |
| 修法①（300 步 / 1000 步） | 0.98 / 1.09 | 1.55 / 0.92 |
| 修法② | 0.93 / 1.07 | 1.20 / 1.28 |
| 修法③ | 1.02 / 1.15 | 1.23 / 0.97 |
| v7x 8 个设备，不做梯度累积（每卡 8192 个下标），不修 | 超，r 4.06，R 6.90 | **在噪声内**，r 0.89，R 1.10 |

- v5p 上两个版本结论相同：不修就超，三种修法都和 GPU 重跑分不开。离线编译也看到，v5p 上各种跑法那次 scatter 排不排序两个版本一样（mini 的表形状；生产形状见下一条）。
- v7x 上不做梯度累积时，每卡 8192 个下标在 0.0.52 上过了排序门槛，词嵌入梯度不再丢精度；0.0.46 上不过线。这是这两个版本、这个配置下的实测，不说明别的跑法、别的版本也这样。生产形状上就搬不过去：词表 120832 × 隐藏维 6144、纯数据并行每卡整张表时（每卡下标数 = 序列长 × 每卡微批），0.0.46 上 v5p、v7x 达到 15105 个就排序，0.0.52 上 v5p 到 65536 个都不排序、v7x 要到 43648 个（单算子离线编译，[`emb-scatter-sort-hy4-prod.json`](../results/emb-scatter-sort-hy4-prod.json)）。所以序列 4096、每卡微批 1–3（每卡 4096–12288 个下标）时 0.0.46 也不排序；每卡 16384 个下标这种跑法 0.0.46 上排序、0.0.52 上反而不排序；0.0.52 的 v5p 上到每卡 65536 个都不排序（更多没量）。生产上纯数据并行照样要修。换版本先看 HLO 里那次 scatter 有没有 `sort` 和 `indices_are_sorted=true`，再按尺子重测。
- 修法③依赖每张卡那次 scatter 的下标数过门槛。0.0.52 上 v5p 列数 128 的表门槛降到 1783，比 0.0.46 更容易过；v7x 上这张表交给 SparseCore 执行，两个版本都排序（HLO 可见，离线编译）。修法③只在 v5p 8 卡上训练过；v7x 上、16 卡以上（每卡列数 1024 ÷ 数据并行份数变小）都没训练过。
- 生产形状下修法③排序（单算子离线编译，同上那份结果文件；只编了词嵌入反向那一个 scatter，整步训练程序没在生产形状上编过，也没上卡）：数据并行 8 时每卡 6144 ÷ 8 = 768 列，那次 scatter 收齐 8 张卡的下标（序列长 × 每卡微批 × 8，序列 4096、每卡微批 1 时 32768 个）。v5p 上门槛 0.0.46 是 15105、0.0.52 是 10815，都过；v7x 上这张表交给 SparseCore，两个版本都排序。0.0.52 上不排序的是不开修法、整表的纯数据并行（上一条）。
- 数据并行不是 8 时换算：修法③每卡列数 = 6144 ÷ 数据并行份数，下标数 = 序列长 × 每卡微批 × 数据并行份数；门槛随列数变，只量了 768 列这一格，别的列数在训练镜像里编一次：`JAX_PLATFORMS=cpu python models/hunyuan4/analysis/emb_scatter_sort_probe.py check --vocab 120832 --dim <6144 ÷ 数据并行份数> --n <下标数> --bisect`，看输出的 `"sorted"`（v7x 上标 `"sparsecore"` 的也是排序）。
- v7x 不累积那一行 0.0.52 的「在噪声内」靠 iHC 豁免：`hc_head` 三个张量离 FP64 0.56–0.62，对照只有 0.014–0.045，按 TPU 自比的 iHC 豁免单列（这是另一条规则：iHC 张量一律不算未定责，没有倍数上限；与 mini 的 D11 条文不同；是否收窄待拍板；[MATRIX V 节](../MATRIX.md#v--libtpu-0052-上重测)）。词嵌入梯度不再变远这一条不受影响。

## 能不能忍

不能。这是固定方向的系统偏差：第 1 步词嵌入梯度离 FP64 是 GPU 的 3.6 倍，300 步曲线 r 2.62，超出噪声上限两倍多。方向固定，推断会随训练累积（不修的纯数据并行没跑过 1000 步）。

## 怎么修

三种，精度上效果一样。三个开关只在 `maxtext` 的混元 4 集成分支上，上游 MaxText 没有，照抄会报未知键；用上游的怎么办见 [MaxText 说明「这些开关在哪个分支」](../../../frameworks/maxtext/README.md#这些开关在哪个分支)。

| 修法 | 做法 | 第 1 步词嵌入梯度离 FP64 | 曲线最差 r |
|---|---|---|---|
| ① `embedding_grad_fp32` | 从 FP32 主权重表取行、再转 BF16。前向逐位不变，反向的累加落在 FP32 | 3.79e-3 | 8 卡 300 步 0.98、1000 步 1.09；16 卡 0.99 / 1.30；不做梯度累积 1.01 |
| ② `embedding_grad_fp32_local_bf16_comm` | 本卡在 FP32 里累加，舍一次 BF16，再用 BF16 跨卡求和 | 4.24e-3 | 300 步 0.93、1000 步 1.07 |
| ③ `embedding_shard_over_data` | 只把词嵌入表沿数据并行轴切开，其余参数仍是纯数据并行；编译器对这张表生成和 FSDP 一样的「先传后加」：交换原始 token 梯度，排序后一次 scatter（[案例 14 第二阶段](../../../cases/14-ddp-fsdp-embedding.md#第二阶段只把词嵌入表沿数据并行轴切开)） | 3.97e-3 | 300 步 1.02、1000 步 1.15（都和 GPU 重跑分不开） |

修法③ 和 ZeRO-1（`shard_optimizer_over_data`）互斥，配置检查直接拒绝（[案例 14](../../../cases/14-ddp-fsdp-embedding.md#第二阶段只把词嵌入表沿数据并行轴切开)）；开着 ZeRO-1 时用修法①。ZeRO-1 本身的精度没测（B1c 在本仓库训练入口上没跑通）。

还有一种没在训练里试过的办法：在 JAX 里先把 token 号排好序，并标上「下标已排序」，让本卡这次 scatter 也走 FP32 累加的写法。单算子里有效：8 卡纯数据并行离 FP64 7.17e-3 → 2.86e-3（同条件 FSDP 1.58e-3），舍入结构和修法② 相同；一次 scatter 多 0.14 ms，估算约占步时的 1e-3。但它依赖 excess precision 开着、libtpu 的这种写法不变，要改 MaxText 词嵌入的反向，没在训练里验证过。见 [B1 梯度的跨卡归约](../b1-grad-reduction.md)第七节。

## 代价

步时（8 卡，按芯片·秒对 golden）：不修 −3.4%，修法① −2.8%，修法② −2.6%，修法③ −3.3%。修法①②本身多 0.6–0.8 个百分点，修法③和不修一样快。

词嵌入梯度整表求和的字节数（每步每设备，按训练步 HLO 的形状算）：不修、修法①、修法②都是 9.90e8。修法①里编译器把主输入和 MTP 两路合成一次 FP32 all-reduce，每个微批 1 次，默认是每个微批 2 次 BF16，所以字节数相同；只有一路输入的模型，修法①会多传一倍（推断）。修法①另在 scatter 前多 16 次 `collective-permute`（token 梯度、id 各 8 次，6.72e7 字节），全部集合通信 2.70e9 → 2.77e9（+2.7%）；修法②全部通信 2.70e9（+0.2%）。修法③不再整表求和，词嵌入的通信降到 6.82e7，全部集合通信从 2.70e9 降到 1.78e9；显存峰值从 6.16e9 降到 4.46e9。

## 坑

修法①在「数据并行 + 梯度累积」下原来有个 bug：编译器把累加器挪出循环后每次清零，丢掉了前面微批的梯度（r 611）。MaxText `d5c9b113` 起已修；修后 golden 重跑逐位相同。根因与修法见[实验矩阵「已修」](../MATRIX.md#已修)。

## 一句话

纯数据并行让词嵌入梯度丢精度，影响是噪声上限的 2–4 倍（v5p 上 libtpu 0.0.46、0.0.52 都实测如此；v7x 不做梯度累积的跑法 0.0.52 上不再丢）；打开 FP32 词嵌入梯度就修好，代价不到 1%；只把词嵌入表沿数据并行轴切开也修好，而且少传 93% 的词嵌入通信、不增加步时。
