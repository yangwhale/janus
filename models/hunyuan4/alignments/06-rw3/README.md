# 混元 4 · 06 · 真实宽度三层：多机 GPU golden ↔ TPU 回放

hy4-preview 的真实权重截第 0–2 层 + MTP（3.21e10 参数；比 T2 多一层 MoE，且第 2 层是 shared 索引器层），GPU 在 2 台 B200 上跑 1000 步作 golden，TPU（v5p 16 片）原样回放它的数据，判法同 01-mini（尺子换成 2 台同设置 8 份两两 28 对，见 [`setup.md`](setup.md#怎么判)）。下表的级别：L0 地基（检查点、设置），L3 第一步整网，L4 训练曲线。设置见 [`setup.md`](setup.md)，运行登记 [`runs.yaml`](runs.yaml)。 结论在 TPU 一侧 libtpu 0.0.46、jax 0.11.1 上测得（[版本](setup.md#软件版本)），换 libtpu 或 jax 要按 [`libtpu-052.md`](../04-tpu-self/libtpu-052.md) 的做法重测。

### 从存档续跑为什么装不下（已修）

**原因**：`train_hy4.py --resume` 先用 `state.to_pure_dict()` 取每个叶子的形状和切分。这个字典的叶子就是状态里的数组本身，不是拷贝。换进存档的值以后，字典一直活到训练结束，旧的初始状态因此整份留在设备上。

- 一份训练状态每设备 1.64e10 字节（15.3 GiB）。从头跑时装载训练步前设备上有一份，续跑时有两份：分配器记的在用量是 3.29e10 字节，正好两份。
- 训练步要预留 72.8G 临时区。从头跑放得下，多一份状态就只剩 65.1G。

**修法**：只留形状、dtype、切分，先释放旧缓冲区，再按目标切分直接读进设备；换进去以后不再留引用。读档期间设备上也只有一份状态。另在建好状态后、读档后各记一次本设备上活着的数组和运行时显存，写进 `meta.json` 的 `memory_probe`。

**核对**（[`resume-check.json`](results/resume-check.json)）：

| 核对 | 结果 |
|---|---|
| CPU（截层 D 的小维度，8 个假设备）：读档后活着的数组 | 修前 580 个、7.94e6 字节，是从头跑的两倍；修后 290 个、3.97e6 字节，与从头跑相同 |
| CPU：跑 20 步 对 跑 10 步存档、再续 10 步 | 第 11–20 步逐步记录全同，最终状态清单全同 |
| TPU 16 片：同一份第 100 步存档续跑（`rfx-v-s1`） | 读档后在用 1.64e10 字节（一份状态），训练步装得下 |
| TPU 16 片：续跑的第 101–250 步 对 不中断的 `b2r-on` | 150 步、每步 40 个字段逐位相同；第 250 步参数清单 9 个文件逐字节相同；跑完时显存与 `b2r-on` 相同（在用 1.74e10、峰值 3.03e10） |

## 第 1 步主 loss 为什么 TPU 偏低

**结论**：几乎全部来自 splash 注意力内核的 base2 模式（MaxText 默认，对齐配置开着）。它把每一层注意力的打分整体放大了 1.0018 倍，注意力略微变尖，主 loss 就低了约 1e-4。TPU 上只关这一个开关重跑第 1 步，主 loss 离 FP64 从 −9.87e-5 变成 −1.24e-6，比 GPU（+5.3e-5）近得多：R 1.85 → 0.02（R 以 GPU 4 份的中位数作分母；只对 `rw1k-a` 是 1.71 → 0.02）。这和事先用 CPU 模拟扣出来的预测（−1.8e-6；按完整模拟扣是 +1.1e-7）对得上。把握：高。内核的算法在 CPU 上核过（见「机制」），截层 B 和 D3 各有一次只差这一个开关的 TPU 实测，量级都和 CPU 模拟相符。

**机制**：内核写的是 `q *= LOG2E`。q 是 BF16，JAX 把 Python 常数按 q 的类型转成 BF16，乘进去的是 1.4453125，不是 log2(e) = 1.442695…，大了 1.81e-3；后面 exp2 换回自然底、sink 却都按精确的 log2(e)。等于每个注意力层的 logits（不含 sink）乘 κ = 1.0018。另外 q 乘完再舍一次 BF16，这一半是逐元素的舍入误差。CPU 上用 Pallas interpret 跑同一份内核源码：base2 的 logsumexp 对「q × 1.4453125 舍 BF16、再除以 log2 e」的 FP64 参照最大差 8.1e-7，对精确 softmax 差 1.3e-3（合成输入；[`splash-base2-probe.json`](results/splash-base2-probe.json)）。

**证据**：主 loss 对 CPU FP64 的相对差（(x − FP64) ÷ FP64；[`step1-base2-emulation.json`](results/step1-base2-emulation.json)）。「CPU FP64 只加 κ」是在 FP64 前向里只把 logits 乘 κ，其余不动。

| 截层 | 哪一份 | 主 loss 相对差 |
|---|---|---|
| D3 | TPU `trw-e`（base2 开） | −9.87e-5 |
| D3 | GPU `rw1k-a` … `rw1k-d` | +5.1e-5 – +5.8e-5，中位数 +5.33e-5 |
| D3 | CPU FP64 只加 κ（4 个注意力层） | −9.69e-5；16 行每行都为负（−7.2e-5 – −1.22e-4） |
| D3 | TPU 减去上一行（推断：两处差可加） | −1.8e-6，R 0.03 |
| D3 | CPU FP64 完整模拟 base2（q 舍 BF16 → 乘 1.4453125 再舍 → 除以 log2 e）减去只把 q 舍 BF16 的对照 | −9.88e-5（完整 −9.885e-5，对照 −2.2e-8） |
| D3 | TPU 减去上一行（推断） | +1.1e-7，R 0.002 |

| B | TPU 只关 base2（`tnorm-sg` → `tqa-nb2`，已有运行，只差这一个开关） | −8.06e-5 → +7.3e-6，移动 +8.79e-5 |
| B | CPU FP64 只加 κ（2 个注意力层） | −8.41e-5；16 行每行都为负 |

| B | GPU `gb2-a` … `gb2-h` | +6.46e-5 – +6.58e-5 |

B 上 CPU 模拟出的移动是 TPU 单开关实测的 0.96 倍（只加 κ）和 0.94 倍（完整模拟减对照），说明模拟抓住的就是 TPU 上那个开关的效果；D3 再用同一种模拟。系统性的部分几乎全在 κ：q 那一次逐元素舍入只多贡献 −2.0e-6（D3）和 +1.3e-6（B），逐行在 ±2e-5 内来回。B 的 TPU 主 loss 由 `diag_step1.json` 的总 loss 减 KD 项得出（推导写在 [`step1-base2-observed.json`](results/step1-base2-observed.json)）。

**逐层**：只在一层乘 κ，D3 主 loss 的移动（16 行；MTP loss 一并列出）：

| 只加在 | 主 loss | MTP loss |
|---|---|---|
| 第 0 层（稠密） | −3.32e-5 | −2.86e-5 |
| 第 1 层（MoE，full 索引器） | −5.77e-5 | −6.11e-5 |
| 第 2 层（MoE，shared 索引器） | −8.4e-6 | −1.93e-5 |
| MTP 层 | 0（MTP 层在主 loss 之后） | −4.47e-5 |
| 四层一起 | −9.69e-5 | −1.31e-4 |

主 loss 三层之和 −9.93e-5，与四层一起差 2.4e-6，基本可加；第 1 层占六成，第 2 层最少。MTP loss 同号、量级相符（TPU 实测 −9.88e-5），但它逐行在 −5.7e-4 到 +1.9e-4 之间跳，GPU 4 份之间就差 1.4e-4（−1.04e-4 到 +4.1e-5），这一项分不细。

**为什么 mini 上没看出来**：放大的效果和 logits 本身的大小成正比。mini 第 1 步全局最大 logit 0.129（[`t1-qkclip-same-state.json`](../01-mini/results/t1-qkclip-same-state.json)），真实权重截层 B 逐头最大 logit 最大 14.5、中位数约 7（`tb6diag` 的第 1 步记录）。同一个 κ，在 mini 上让指数最多变 2.3e-4，在真实权重上到 2.6e-2。这是真实权重的分布才显形的机制，和累加长度无关。

**意味着什么**：开着 base2 时，真实宽度上 TPU 每一步的注意力都略尖，第 1 步主 loss 因此偏低约 1e-4。前 164 步 TPU 主 loss 同号偏低（带符号均值 −8.7e-5）只有一部分来自这里：后来补的 base2 开 / 关 250 步回放里，关掉后前 164 步主 loss r 17.8 → 10.7，偏低变小但没有消失，base2 的影响主要在前约 100 步，其余是轨迹差（[base2 开 / 关的 250 步回放](#base2-开--关的-250-步回放)、[后段主 loss 偏低](#后段主-loss-偏低不是前向的差是轨迹的差)）。对齐配置 2026-11-11 起所有尺寸都关 base2。

### TPU 实测：D3 只关 base2

同一个代码包、同一份数据，第 1 步只差 `sa_use_base2_exp`（[`step1-base2-off.json`](results/step1-base2-off.json)）：

| 哪一份 | 主 loss 对 FP64 | MTP loss 对 FP64 |
|---|---|---|
| TPU base2 开（`trw-e`；`b2s1-at` 第 1 步与它逐位相同） | −9.87e-5，R 1.85 | −9.88e-5 |
| TPU base2 关（`b2s1-bt`） | −1.24e-6，R 0.02 | −6.92e-5 |
| 开 → 关的移动 | +9.75e-5（CPU 模拟预测 +9.69e-5 只加放大、+9.88e-5 完整模拟） | +2.96e-5（CPU 模拟预测 +1.31e-4） |
| GPU `rw1k-a` … `rw1k-d` | +5.1e-5 – +5.8e-5，中位数 +5.33e-5 | −1.04e-4 – +4.1e-5，中位数 −4.3e-5 |

主 loss 的移动是 CPU 模拟预测的 1.006 倍（只加放大）和 0.99 倍（完整模拟）；截层 B 上实测是预测的 1.05 和 1.06 倍，两个截层都在 ±6% 以内。MTP loss 没按预测移动（实测 +2.96e-5，预测 +1.31e-4），但它本来就分不细：CPU 模拟里逐行在 −5.7e-4 到 +1.9e-4 之间跳，GPU 4 份之间差 1.4e-4；关掉以后 TPU 的 −6.92e-5 落在 GPU 4 份的范围内，对 GPU 中位数绝对值的比 1.15。

### 逐张量梯度

两份 TPU 都用 `--diag-step1` 存下第 1 步的梯度（路由专家以外 102 个张量；路由专家每层是一个 256 × … 的融合张量，FP32 约 39 GB，没存），对 CPU FP64 整网反向（同一份 Megatron-Core 代码，路由专家只算第 0 号的权重梯度，其余参数全算）。分母都是 ‖FP64‖。

| 模块 | 张量数 | base2 开 对 FP64 | base2 关 对 FP64 | 关 ÷ 开（中位数） | 关后更近的个数 | 开 对 关 |
|---|---|---|---|---|---|---|
| 全部 | 102 | 2.03e-3 | 1.72e-3 | 0.86 | 86 | 1.27e-3 |
| 注意力 | 28 | 2.44e-3 | 1.78e-3 | 0.80 | 26 | 1.73e-3 |
| norm | 20 | 2.80e-3 | 2.18e-3 | 0.93 | 20 | 2.82e-3 |
| MLP / 共享专家 / 路由 | 15 | 1.36e-3 | 1.11e-3 | 0.82 | 15 | 1.09e-3 |
| iHC | 21 | 8.77e-4 | 7.64e-4 | 0.82 | 14 | 5.97e-4 |
| 索引器 | 15 | 2.43e-3 | 2.41e-3 | 0.99 | 8 | 8.34e-4 |

- 收得最多的是 q 一路与 sink：第 0、1 层 `q_a_layernorm` 3.49e-3 → 1.68e-3、3.95e-3 → 2.02e-3（截层 B 同一张量 3.09e-3 → 9.42e-4），第 1 层 `q_b_proj` 3.85e-3 → 2.17e-3，第 0、2 层 sink 2.40e-3 → 1.29e-3、3.92e-3 → 1.61e-3。
- 索引器不动：它的输入在 KD 里 detach，打分也不走 splash。
- 关后反而远的 11 个：MTP 层的 sink 4.81e-3 → 9.37e-3；其余 10 个是 iHC 的标量（`hc_scale` / `hc_base` / `hc_fn`）、第 1 层索引器的 `k_norm` 和第 2 层 `q_b_proj`，变得最多的是第 0 层的两个 `hc_scale`：2.69e-4 → 6.74e-4、2.79e-3 → 4.02e-3。MTP 层 sink 的变化在 GPU 重跑噪声内（见下文「关掉以后还剩什么」）。
- GPU 一侧补了第 1 步逐张量抓数：单机 DP 8 + EP 8 同设置 3 份（`r3s1-a` … `r3s1-c`，`--dump-steps 1 --full`；第 1 步主 loss 对 FP64 +5.57e-5 – +5.65e-5，与 2 台的 `rw1k-*` 同号同量级）。GPU 对 FP64 的 rel_L2 中位数 1.39e-3，三份两两最大差的中位数 5.8e-4。R = rel(TPU, FP64) ÷ 中位数 rel(GPU, FP64)（[`step1-tpu-gpu-vs-fp64.json`](results/step1-tpu-gpu-vs-fp64.json)）：

| 模块 | GPU 对 FP64 | R 中位数（开 → 关） | R > 1.2 的个数（开 → 关） |
|---|---|---|---|
| 全部（102） | 1.39e-3 | 1.06 → 0.92 | 38 → 25 |
| 注意力（28） | 1.6e-3 | 1.11 → 0.90 | 10 → 4 |
| norm（20） | 1.5e-3 | 1.60 → 1.45 | 14 → 12 |
| MLP / 共享专家 / 路由（15） | 1.3e-3 | 0.98 → 0.83 | 0 → 0 |
| iHC（21） | 1.0e-3 | 1.01 → 0.99 | 10 → 6 |
| 索引器（15） | 2.0e-3 | 0.64 → 0.64 | 4 → 3 |

关掉 base2 后 TPU 整体与 GPU 相当（R 中位数 0.92）；剩下明显不如 GPU 的是 norm 的权重梯度（RMSNorm 权重梯度，根源第 23 行），R 最大的是第 2 层 `kv_a_layernorm` 2.52、第 0 层 `post_attention_layernorm` 2.17、`model.norm` 2.01。

**base2 解释了多少**：CPU FP64 整网反向里只加放大 κ（4 个注意力层），再拿 base2 开的那份去比。FP64 本身被 κ 移动的中位数是 9.1e-4。

- base2 开那份对「FP64 + κ」的中位数是 1.81e-3，比对原 FP64 的 2.03e-3 近；102 个里 76 个更近。
- 关掉后对 FP64 是 1.72e-3。按中位数粗算，开 → 关的改善（2.03e-3 → 1.72e-3）约七成能由 κ 解释（2.03e-3 → 1.81e-3）。剩下的推断来自 q 多舍的那一次 BF16，这次的 FP64 模拟没包含它（见下一段）。
- TPU 开 − 关的差和 κ 在 FP64 里造成的移动，方向大体一致：夹角余弦中位数 0.63，iHC 0.92，注意力 0.67，MLP 0.66，norm 只有 0.27。
- 第 0 层索引器的 5 个张量开、关逐位相同。它的 KD 输入 detach，又在第 0 层注意力之前算，不经过 splash，与机制相符。
- 注意力一组里 28 个有 20 个更靠近「FP64 + κ」，但中位数反而变大（2.44e-3 → 2.78e-3）：几个大张量只加 κ 时偏得更远，q 那一次舍入在这一组不能忽略（推断）。

这次 FP64 那份命令写的是完整模拟（`--emulate-base2 full`），但和 `--audit` 一起用时，q 的 BF16 舍入被改回了 FP64，实际只加了 κ。它的主 loss 与只前向的 κ 模拟逐位相同（12.013328636119082）。`step1_ref.py` 现在拒绝这种组合。

**关掉以后还剩什么**：

- 主 loss：−1.24e-6，R 0.02，已在 FP64 旁边。
- MTP loss：−6.92e-5，在 GPU 4 份的范围内。
- 逐张量梯度：中位数 1.72e-3，和其他真实宽度截层上 GPU 对 FP64 的量级相同（见上）。各模块里最远的是 norm（2.18e-3，根源第 23 行的 RMSNorm 权重梯度）和 MTP 层（逐层中位数 3.46e-3）。索引器不受 base2 影响，仍是 2.41e-3。
- MTP 层的 sink 关后从 4.81e-3 变成 9.37e-3，但这个张量的梯度很小（范数 2.4e-4，是第 2 层 sink 的 1/40），GPU 三份之间就差 8.27e-3；TPU 关那份离最近一份 GPU 7.67e-3，是 GPU 两两最大差的 0.93 倍，在 GPU 重跑的噪声内（R 1.72 是分母小造成的）。这一条不是真变坏。
- 对 GPU：剩下超过 GPU 的主要是 norm 一组（见上表），与 base2 无关。

## base2 开 / 关的 250 步回放

两臂同一个代码包（与 `trw-e` 同），回放 `rw1k-a` 的前 250 步，只差 `sa_use_base2_exp`；同在 v5p 2x2x4 上一次跑完，不存档。判法同 01-mini：GPU `rw1k-a` 作基线，噪声上限 N 取 GPU 8 份（`rw1k-a` … `rw1k-h`）两两 28 对在同一窗口上的最大值（[`rw3-l4-b2r250.yaml`](catalogs/rw3-l4-b2r250.yaml)）。r = TPU 对 GPU 的差 ÷ N，三个判定量里取最大；≤ 1 过，1–2 待定，> 2 不过。

前 164 步（与 `trw-e` 的中间判档同一窗口，[`rw3-l4-first164`](results/rw3-l4-first164.report.md)）：主 loss r 17.8 → 10.7、MTP 3.39 → 1.02、param_norm 6.28 → 2.42，索引器 KD 4.72 → 11.5；主 loss 两臂相减 −3.45e-5，7.1 个 N。

**前 164 步那段的同号偏低，关掉 base2 后没有消失，只是变小了。**

- **前约 100 步**：base2 的影响主要在这一段。主 loss 两臂之差在 1–164 步是 7.1 个 N，到 101–250 步只剩 0.1 个 N。第 1 步关掉后 TPU 已在 FP64 旁边（[上一节](#tpu-实测d3-只关-base2)），剩下对 GPU 的 −5.9e-5 正好是 GPU 自己比 FP64 高出的那一截（+5.3e-5）。
- **后段（101–250 步）**：两臂都是 −2.5e-5，约 2.7 个 N，而且两臂一样。这一段的偏低不是 base2 造成的，原因还没查。
- **MTP loss 和 param_norm**：关掉后都回到噪声以内，或接近噪声。
- **索引器 KD**：关掉后变坏，从略偏高变成偏低 3.53e-4。只看第 1 步时，KD 对 FP64 是 GPU +8.3e-4、TPU 开 +2.9e-4、关 +1.7e-4：关掉的 TPU 离 FP64 最近，离 GPU 最远。多步上是不是同一个原因，没有验证。
- **路由偏置均值**：两臂都待定，关掉后略差（1.05 → 1.55）。

两臂第 1、2 步与 `b2s1-at` / `b2s1-bt` 逐位相同；`b2r-on` 前 164 步与 `trw-e` 逐位相同，同一配置在同一种切片上重跑可复现。

## 后段主 loss 偏低：不是前向的差，是轨迹的差

250 步回放的后段（第 101–250 步），两臂主 loss 都比 GPU 低约 2.5e-5（约 2.7 个 N），与 base2 无关。下面三步把它拆开。

**1. 偏差从第 1 步就有，随训练变小**。TPU base2 关对 GPU 8 份逐步均值的相对差（窗口内平均；GPU 一列是 8 份各自窗口均值的标准差）：

| 窗口 | 1–10 | 11–50 | 51–100 | 101–150 | 151–200 | 201–250 |
|---|---|---|---|---|---|---|
| TPU base2 关 | −5.91e-5 | −5.00e-5 | −7.21e-5 | −4.55e-5 | −3.04e-5 | −5.97e-6 |
| TPU base2 开 | −1.50e-4 | −1.24e-4 | −9.77e-5 | −5.78e-5 | −2.51e-5 | −1.53e-6 |
| GPU 8 份的散布 | 1.3e-6 | 1.6e-6 | 2.8e-6 | 2.7e-6 | 3.7e-6 | 5.7e-6 |

到第 201–250 步两臂都回到 GPU 散布的量级。param_norm、路由偏置、索引器 KD 都没有比主 loss 更早动的。

**2. 同一份权重，TPU 算得比 GPU 高，不是低**。取 TPU base2 关第 150 步更新之后的权重（`train_hy4.py --hf-snapshot-at 151` 按 HF 检查点格式导出），在第 151 步的同一批数据上，TPU、GPU、CPU FP64 各算一次前向（[`rw3-step151-same-state.json`](results/rw3-step151-same-state.json)）：

| 哪一份 | 主 loss 对 FP64 | MTP loss 对 FP64 |
|---|---|---|
| TPU 自己（训练步记录，权重是 FP32 主权重） | +3.68e-5 | +9.0e-6 |
| GPU 2 台，同一份权重（输出头、索引器 k_norm 留 FP32 主权重原值，同 GPU 训练时） | +2.11e-5、+2.22e-5 | −3.7e-5、−2.0e-5 |
| CPU FP64 | 6.594300 | 0.732144 |

同一份权重上 TPU 比 GPU 高 1.5e-5。后段 TPU 偏低（第 141–161 步对 GPU 8 份均值 −3.4e-5）因此不是前向的计算差，而是 TPU 走到的状态本身 loss 更低：按 GPU 的前向量，TPU 的这份权重比 GPU 8 份第 151 步的均值低 2.2e-5（单步 GPU 散布 1.9e-5，单看一步分不开，窗口平均里分得开）。按窗口估：−3.4e-5（量到的差）减去 +1.5e-5（前向差）≈ −4.9e-5 是状态差（推断，前向差只量了一批数据）。

第 1 步的情况正相反：那时权重相同，TPU（关）对 FP64 −1.2e-6、GPU +5.3e-5，前 10 步的 −5.9e-5 几乎全是 GPU 前向偏高。前向偏差随训练变化（到第 151 步 GPU +2.2e-5、TPU +3.7e-5），轨迹差在中段长起来、后段又收回去。

第 1 步 GPU 的 +5.3e-5 拆不出单一算子。同一套 Megatron-Core 代码在 CPU 上按 GPU 写法跑 BF16 前向，能复现 +5.21e-5。再在 FP64 前向里每次只加一类 BF16 舍入（16 行，比例按 +5.21e-5 算；[`step1-main-loss-bf16-sites.json`](results/step1-main-loss-bf16-sites.json)）：

- MLA 主注意力 q_pe、k_pe 的 BF16 RoPE：+8.74e-6（17%）。它和索引器 KD 偏高是同一个函数（`_apply_rotary_pos_emb_bshd`）。
- 线性层、norm、注意力核输出一起舍：+1.26e-5（24%）。只舍线性层是 −7.65e-6。
- 层间残差流：+5.02e-6（10%）。
- 输出头输入：+1.87e-6（3.6%）。
- k_pe 存储：+1.45e-6（2.8%）。
- 注意力概率：+1.6e-7（0.3%）。

简单相加约 55%，各类不一定可加。剩下的估计在 SwiGLU、输出门、iHC 内部、MoE 合并这些逐元素运算里，都没测（推断）。

**3. 权重精度只有输出头一处起作用**。同一份 TPU 权重上把各组参数分别舍成 BF16 再前向（`--eval-variants-at 151 --eval-variants=@weight-side`，[`b2e-off151-eval-variants-step151.json`](results/b2e-off151-eval-variants-step151.json)）：只有输出头改了主 loss，舍成 BF16 后升 1.780e-4；CPU FP64 里同样把输出头舍成 BF16，升 1.775e-4。其余各组（嵌入、norm、注意力、索引器、MLP、路由专家、路由、MTP）对主 loss 是 0 或 −1.4e-6；舍 k_norm 让 KD 变 +5.45e-3。GPU 的输出头和 k_norm 也留 FP32，所以这两处两边语义相同。第一次做同状态对照时，快照把这两处舍成了 BF16，GPU 量到 +2.8e-5、TPU 舍同样两处后 +4.2e-5，结论相同（TPU 高 1.4e-5）。

已排除：base2（两臂后段相同）；同一份权重上的前向计算（TPU 高、不是低）；权重侧精度（只有输出头起作用，GPU 也是 FP32）。轨迹差的来源见下一段。

**4. 轨迹差不是索引器造成的**。GPU 一侧索引器 KD 偏高定位到索引器的 RoPE 在 BF16 里算（cos、sin 与乘加都是 BF16，见下文「索引器 KD」一节）。把 GPU 的这一处改到 FP32 里算、结果舍一次，跑 250 步两份（`irf-a`、`irf-b`，同 `rw1k-*` 的设置，对 `rw1k-a` 与同一把尺子）：

| 检查 | `irf-a` | `irf-b` | TPU base2 关 |
|---|---|---|---|
| 索引器 KD（第 1–250 步，带符号均值） | ❌ −4.18e-4（r 2.76） | ❌ r 3.07 | ❌ −3.53e-4（r 2.33） |
| 主 loss（第 1–250 步） | ✅ 0.88 | ✅ 0.86 | ❌ 7.32 |
| 主 loss 后段（第 101–250 步）对 GPU 8 份均值 | +1.8e-6 | −1.2e-6 | −2.73e-5 |

KD 降到与 TPU 同一侧，主 loss 一点没动（[`irf-a`](results/rw3-l4-b2r250-irf-a.report.md)、[`irf-b`](results/rw3-l4-b2r250-irf-b.report.md)；param_norm 一项报错是因为 GPU 没有 TPU 的那一列，不影响别的项）。所以 GPU 的 KD 偏高是真的、在 GPU 一侧，但它不是主 loss 轨迹差的原因。


**5. 同一份权重上的梯度：iHC 一组两边一高一低**。同一份第 150 步之后的权重、第 151 步的批，TPU（`--diag-step1`，从快照换上权重）、GPU 单机 2 份（`--dump-steps 1 --full`）、CPU FP64 整网反向，逐张量比 102 个非路由专家张量（[`rw3-step151-same-state-grads.json`](results/rw3-step151-same-state-grads.json)）：

| 组 | iHC 梯度平方和 | 梯度范数（全部） | TPU 对 GPU 超出 GPU 噪声的倍数（中位数） | R（TPU ÷ GPU，对 FP64，中位数） |
|---|---|---|---|---|
| CPU FP64 | 62.06 | 8.751 | — | — |
| TPU 默认 | 63.80（+2.8%） | 8.850 | iHC 7.5（21 个里 19 个 > 2）；其余组 1.8–2.1 | 全部 1.03；iHC 0.90、注意力 1.03、norm 1.15 |
| TPU 关省舍入（`--xla_allow_excess_precision=false`） | 59.93（−3.4%） | 8.630 | iHC 3.2；其余组 2.0 左右 | 全部 1.30（R > 1.2 的 27 → 64 个） |
| GPU 2 份 | 60.27、60.40（−2.8%） | 8.649、8.666 | — | — |

- 第 1 步时 iHC 平方和两边只差 0.27%；训练后差到约 6%，差得最多的是第 1 层注意力侧 `hc_scale`（TPU 范数比 FP64 大 7.1%、GPU 小 5.0%，两边都偏得多，这个张量本身病态）。
- 关掉 TPU 编译器的省舍入，iHC 平方和就落到 GPU 旁边（59.93 对 60.3）：差别来自 iHC 上 GPU（eager）一定会舍成 BF16、TPU 编译器省掉的那几次舍入，和 TPU 自比查到的「iHC 残差更新 `out = x + post·layer_out`」是同一段（04 的 impacts/02）。但关掉以后其余各组都离 FP64 更远，不能当修法。
- 对 FP64，TPU 默认与 GPU 一样准（R 中位数 1.03，iHC 0.90）：同一份权重上的梯度差，谈不上哪边错。

**6. 关掉省舍入跑 250 步：离 GPU 更远，不是轨迹差的原因**。base2 关的设置再加 `XLA_FLAGS=--xla_allow_excess_precision=false`，跑 250 步（`b2r-noexc`，对 `rw1k-a` 与同一把尺子；[`rw3-l4-b2r250-noexc`](results/rw3-l4-b2r250-noexc.report.md)、两臂对照 [`rw3-b2r-noexc-vs-off.json`](results/rw3-b2r-noexc-vs-off.json)）：

| 检查 | 默认（`b2r-off`） | 关省舍入（`b2r-noexc`） |
|---|---|---|
| 主 loss 第 1–250 步 | ❌ r 7.32，带符号均值 −3.90e-5 | ❌ r 29.6，−1.58e-4 |
| 主 loss 第 101–250 步 | ❌ r 2.72，−2.51e-5 | ❌ r 13.2，−1.22e-4 |
| MTP loss 第 1–250 步 | ✅ r 0.99 | ❌ r 5.79 |
| 索引器 KD 第 1–250 步 | ❌ r 2.33，−3.53e-4 | ❌ r 3.06，+4.63e-4 |
| grad_norm / param_norm | ✅ 0.87 / 0.67 | ⚠️ 1.45 / 1.87 |

对 GPU 8 份逐步均值的主 loss 相对差（窗口内平均）：

| 窗口 | 1–10 | 11–50 | 51–100 | 101–150 | 151–200 | 201–250 |
|---|---|---|---|---|---|---|
| 默认 | −5.91e-5 | −5.00e-5 | −7.21e-5 | −4.55e-5 | −3.04e-5 | −5.97e-6 |
| 关省舍入 | −3.44e-5 | −1.27e-4 | −3.18e-4 | −2.18e-4 | −1.07e-4 | −4.65e-5 |

同一份权重上关掉省舍入让 iHC 梯度靠向 GPU，但别的组离 FP64 更远（上一条，R 1.30），跑起来轨迹偏得更多、方向相同。所以 iHC 那几次舍入不是后段偏低的原因；TPU 默认的编译结果反而是离 GPU 最近的那一种。

已排除（到这里为止）：base2；同一份权重上的前向计算；权重侧精度；GPU 索引器 RoPE；iHC 上编译器省掉的舍入。还没查的：路由专家的梯度（TPU `--diag-step1` 不存，同状态对照里没有）；同一份梯度上的优化器更新与路由偏置更新。

## MTP loss 全程偏低：主要是轨迹，同一份权重上的前向差不显著

1000 步里 MTP loss 两臂每个窗口都偏低（base2 开 r 3.17、关 1.85）。按「后段主 loss」那一节的办法，在同一份权重上让 TPU 和 GPU 各算一次前向，看偏低有多少是每一步都有的计算差（[`rw3-mtp-same-state.json`](results/rw3-mtp-same-state.json)）。

**做法**：取 TPU base2 关（`rfx-off`）第 900 步的存档续跑一步，按 HF 格式导出权重（同第 151 步的 v2：BF16，输出头与索引器 k_norm 用 FP32 原值）。GPU 2 台载入这份权重，111 个张量 sha256 全对，第 901 步 16 行的 tokens 指纹与 TPU 相同。单批噪声太大（见下），所以两边都把学习率和路由偏置更新率设成 0，在同一份权重上连算 8 批（第 901–908 步的数据），再加到 32 批（第 901–932 步）。param_norm 8 步不变，确认权重没动。TPU 续跑的第 901 步与 `rfx-off` 逐位相同。

| 同一份权重（第 900 步之后） | 主 loss | MTP loss |
|---|---|---|
| TPU 对 GPU 2 份均值，8 批平均 | −3.6e-6 ± 4.9e-6 | −2.18e-5 ± 1.24e-5 |
| TPU 对 GPU 2 份均值，32 批平均 | +1.0e-6 ± 3.8e-6 | −1.02e-5 ± 7.5e-6 |
| 32 批里 TPU 偏低的批数 | 16 | 19 |
| GPU 两份之间，同一批（均方根，32 批） | 4.8e-6 | 4.7e-5 |
| 轨迹上 TPU 对 GPU 8 份均值，第 751–1000 步（base2 关 / 开） | −2.40e-5 / −3.10e-5 | −4.16e-5 / −5.89e-5 |
| 轨迹上，第 851–950 步（base2 关 / 开） | −2.66e-5 / −3.31e-5 | −3.71e-5 / −6.44e-5 |

±是批间的标准误。TPU 32 批里的前 8 批与 8 批那次逐位相同。

- **主 loss**：同一份权重上 TPU 和 GPU 没有差：8 批平均 −3.6e-6 ± 4.9e-6，加到 32 批 +1.0e-6 ± 3.8e-6，都不到一个标准误，符号也随批数翻过来（32 批里 16 批偏低）。后段的 −2.4e-5 全是轨迹差。这和第 151 步的结论相同，现在在第 900 步上也成立。
- **MTP loss**：8 批时同一份权重上 TPU 低 2.18e-5（1.8 个标准误），加到 32 批后是 −1.02e-5 ± 7.5e-6（1.4 个标准误，32 批里 19 批偏低）。前向差即使存在，也只占轨迹上偏低（base2 关，−3.7e-5 到 −4.2e-5）的约四分之一，统计上不显著。MTP 的偏低主要是轨迹差，和主 loss 一样。
- **base2**：开的那臂轨迹上 MTP 再低约 2e-5（−5.9e-5 对 −4.2e-5）。base2 只在前约 100 步影响主 loss，对 MTP 一直有影响。第 1 步只加 κ 的 CPU 模拟里，MTP 层自己就贡献 −4.47e-5（见[逐层](#第-1-步主-loss-为什么-tpu-偏低)）。
- **以前的单批对照方向相反，是噪声**：第 151 步单批是 TPU 比 GPU 高约 3.8e-5（对 FP64：TPU +9.0e-6，GPU −3.7e-5、−2.0e-5），第 901 步单批是 TPU 低 4.4e-5。GPU 同一份权重、同一批数据重跑，MTP loss 之间就差 5.5e-5（均方根），主 loss 只差 3.7e-6；第 1 步权重全同时，GPU 8 份的 MTP loss 相对标准差 6.1e-5，主 loss 3.0e-6。所以 MTP 的单批对照分不出 2e-5 量级的差，至少要几十批。TPU 一侧同一份权重换一个单独编译的前向，MTP 也会动 2.5e-5（第 151 步：训练步 +9.0e-6，单独编译 +3.45e-5）。
- **为什么 MTP 这么抖**：GPU 的 MTP loss 重跑抖动是主 loss 的 15 倍。推断（没验证）：MTP 层的路由与索引器选择对输入的微小差很敏感，少数 token 换了专家，单层 MTP 没有后续层把差平均掉。

**没拆算子**：32 批上前向差不显著（1.4 个标准误），没有可拆的对象，所以没往 MTP 层的算子（enorm / hnorm、拼接投影、sink、共享输出头）上拆。MTP 和主 loss 的后段偏低一起按轨迹差查。

## 索引器 KD：GPU 一侧偏高，来自索引器 RoPE 在 BF16 里算

第 1 步 KD 对 CPU FP64：GPU 4 份 +8.1e-4 – +8.4e-4（单机 3 份 +8.15e-4 – +8.35e-4），TPU base2 开 +2.9e-4、关 +1.7e-4。关掉 base2 后 TPU 离 FP64 更近、离 GPU 更远，因为偏差主要在 GPU 一侧：

- **定位到的算子**：Megatron-Core `rope_utils._apply_rotary_pos_emb_bshd`（`apply_rope_fusion=False`），经 `Hy4Indexer._apply_rope` 作用在索引器 q、k 的后 64 维（RoPE 段）。它先把 cos、sin 转成 BF16，乘和加也都在 BF16 里做。两处单独都不对，合起来才复现（交互作用）；角度用 FP32 还是 FP64 无关。
- **CPU 上的拆分**（GPU 同一套代码，16 行；[`step1-kd-gpu-bias.json`](results/step1-kd-gpu-bias.json)）：CPU BF16 前向（GPU 写法）的 KD 对 FP64 是 +7.66e-4，复现 GPU。其中学生一侧（索引器 q、k、w）+7.49e-4，教师一侧 +0.93e-4；学生一侧里，索引器 RoPE 换成 FP64 算、结果舍一次，就从 +5.02e-4 降到 +1.1e-6，所以这一处约 +5.0e-4，占 GPU 偏差的六成。其余来自上游输入的累积舍入（+2.5e-4，主要在 MTP 层）和第 0 层教师 k_pe 存 BF16（对总量 +8.9e-5）。
- **GPU 上的实测**：只把这一处改到 FP32 里算（`irf-a`、`irf-b`，上一节），第 1 步 KD 降 4.85e-4，250 步带符号均值降 4.2e-4 – 4.7e-4，落到 TPU 一侧；主 loss 不变。
- **意味着什么**：KD 一项的 TPU 对 GPU 差，大部分是 GPU 的写法离真值远，不是 TPU 的问题；它只影响索引器，不进主 loss。修法（GPU 一侧索引器 RoPE 用 FP32）只作诊断，正式判定照旧。

## 对齐配置要不要关 base2（已定：所有尺寸都关）

**2026-11-11 项目负责人定：所有尺寸的对齐配置都关 base2**（`hy4-t2-d1.yml` 等四份写 `sa_use_base2_exp: false`，[PROTOCOL 变更记录 2026-11-11](../../PROTOCOL.md#7-变更记录)），mini 现行比较换成关 base2 的 `tz-off-rep`（过 7、待定 2，见 [01-mini 对齐报告](../01-mini/ALIGNMENT-REPORT.md)）。本 README 前面各节的 250 步、1000 步回放是在改之前跑的，开、关两臂都在。下面保留当时的证据和建议。

| 证据 | 关 base2 后 | 出处 |

**两个尺寸的结论不矛盾。**

- **mini**：只看 `t1zz-a` 一份时，关掉后离 GPU 更远（r 0.36 → 1.91）。开、关各补到 4 份（另 3 份只改执行方式：关延迟隐藏调度、vmem 上限 32 / 64 MiB）后，这是轨迹偶然：
  - 主 loss r 开 0.90、1.24、1.02、1.69，关 1.55、1.06、0.93、0.95，两组交叠，开的中位数（1.13）还略高于关的（1.01）；
  - 主 loss 对 GPU 均值，组均值开 +4.39e-6、关 +4.24e-6；
  - 8 份 TPU 都偏高，是与 base2 无关的共同偏移（每份 GPU 对其余 15 份只在 ±2.6e-6 内），要另查；
  - mini 第 1 步最大 logit 只有 0.129，放大几乎不起作用；第 1 步对 FP64 开、关同一量级。
- **真实宽度**：放大本身是一个已知的、TPU 一侧的系统误差。关掉以后，第 1 步对 FP64 更准，250 步对 GPU 也是 9 项里 4 项变好、2 项变坏。
- **语义**：GPU 是自然指数、q·k 在 FP32 里算，关掉 base2 的 TPU 在语义上更接近 GPU。

**建议（把握中等偏高）**：选第 3 种，所有尺寸的对齐配置都关 base2。

- 理由一：真实宽度上关掉更接近 GPU 的语义，第 1 步对 FP64 更准，250 步和 1000 步的判档都整体变好（1000 步不过 3 → 0）。
- 理由二：mini 上原来唯一的反对证据已查清是轨迹偶然。开、关各 4 份分不开，关掉不会让 mini 变差。
- 理由三：全部关，各尺寸的配置保持一致，不用在 PROTOCOL 里登记尺寸之间的差别。生产建议本来也是关。
- 代价：mini 现行比较要换成关 base2 的那一代（如 `t1zz-a`）重新判。按上面 4 份的 r，判档会在过与待定之间，取决于选哪一份。
- 不受影响的：主 loss 后段偏低（真实宽度）和 8 份 mini TPU 共同偏高约 +4.3e-6，两件都与 base2 无关，要另查。

三种做法：

1. 维持现状，所有尺寸都开 base2。真实宽度的 L4 带着已知的放大误差判，前约 100 步的主 loss、MTP、param_norm 都会因此不过。
2. 只在真实宽度截层（T2、06）关，mini 维持开。
3. 全部关，mini 现行比较改成关 base2 的那一代，重新判（建议）。
