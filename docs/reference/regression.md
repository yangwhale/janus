# 日常回归验收

**目的**：模型已经在 TPU 上投产，每天都有 PR 合进来。日常回归回答一个问题：**这段时间合进来的代码、库版本、编译开关，有没有悄悄改变数值。**

它和迁移验收（GPU → TPU）是两件事：

| | 迁移验收 | 日常回归 |
|---|---|---|
| 参照 | GPU golden | 本平台、本档位上一次通过的 TPU 运行（last-known-good，下称 **LKG**） |
| 尺子 | GPU 自己重跑的噪声 | 逐位为主；不逐位时用 TPU 自噪声（扰动臂） |
| 频率 | 一次（换平台、换模型、开新配方时重做） | 每次合并、每 2–4 小时、每天 |
| 证明什么 | TPU 和 GPU 训的是同一个模型 | 今天的 TPU 和上一次验证过的 TPU 训的是同一个模型 |
| 放哪 | `models/<模型>/alignments/<实践>/` | `models/<模型>/regression/`（见 [`layout.md`](../dev/layout.md)） |

**标准跨平台统一**：v5p、v7x 和以后的平台用同一张清单、同一套判法。

- 平台只改参数：切片与芯片数、每档步数、标定出来的噪声数、预计时长。
- 每个模型的实例文档里有一张「平台档案」表，一个平台一列（混元 3 见 [`../../models/hunyuan3/regression/README.md`](../../models/hunyuan3/regression/README.md)）。

**本页结构**：一至三讲判法（为什么逐位、三种参照、PR 声明）→ 四是清单 → 五至七讲尺子、档位、LKG → 八至十讲出事以后怎么办 → 十一、十二是报告与常见误判。

## 一、为什么以逐位为主

TPU 上同一程序、同一输入重跑逐位相同（`environment.md`「TPU 侧 · 原则」第一条）。

- 这是前提，每个平台、每一档在建立首个 LKG 时实测一次（第七节）。
- 之后每天由对照臂（R24）复核。

输入钉死以后：

- **判定值一位都没变**：这段时间的改动没碰数值。不需要噪声、不需要统计，结论是确定的。
- **变了**：一定是某个改动或环境变化造成的。
  - 二分的判据是「这一位变没变」，没有噪声干扰，每次二分的结果都可复现。

容差门只用在「已经知道会变」的场合（PR 声明会改数值、升级依赖不逐位）。尺子来自 TPU 自己的扰动臂（第五节），不拍脑袋。

## 二、三种参照

| 参照 | 比谁 | 回答 |
|---|---|---|
| **回归门** | 同平台、同档位、同并行变体的 LKG | 数值变没变；变了是不是在声明的范围和幅度内 |
| **对照臂** | 今天、同一平台上重跑 LKG 的提交 | 环境（镜像、硬件、集群）变没变。对照臂不逐位 = 环境问题，不是代码问题 |
| **对齐门** | GPU golden（迁移验收用的那几份） | 数值变了以后，TPU 和 GPU 的差有没有变大 |

- 回归门逐位通过时，数值和 LKG 一模一样，对齐门的结论直接继承 LKG 的，不用重算。
- 对齐门只在数值变了的时候跑。

## 三、PR 声明

训练代码仓库的每个 PR 在正文里加一栏 `## 数值影响`，三选一。

- 回归系统按合并提交找到 PR，读这一栏。
- 这一栏放进训练代码仓库的 PR 模板，PR 检查（`pr-check`）核它：
  - 动了训练代码或依赖的 PR 必须三选一；
  - 「会改数值」要写幅度、范围、理由；
  - 「升级依赖」要写版本。

### 三种声明

| 声明 | 什么时候用 | 还要写什么 |
|---|---|---|
| **数学不变** | 重构、加日志与监控、改不进训练图的代码、预期逐位不变的性能改动 | 无 |
| **会改数值** | 改精度、算法、公式、默认配置、并行或重算设置；预期会改变融合、调度、分块从而不逐位的性能改动 | ① 幅度；② 范围；③ 理由（见注 1） |
| **升级依赖** | jax / jaxlib / libtpu、kernel 库、checkpoint 库、镜像、编译开关（`XLA_FLAGS`、`LIBTPU_INIT_ARGS`） | 新旧版本号、镜像 digest、变更日志里和数值有关的条目 |

注 1（「会改数值」要写的三项）：

- ① 幅度：
  - `执行级`：只改融合、调度、分块、重算位置，预期在 TPU 执行噪声内；
  - `数学级`：改精度、算法、公式，预期超出执行噪声。
- ② 范围：清单里哪几行会变。
- ③ 理由。

### 规矩

- **没写声明的按「数学不变」判**，这是最严的一档。
- **一个 PR 只做一种事**。
  - 会改数值的改动和性能改动捆在一起，二分时分不开，评审时要求拆开。
- **会改数值、升级依赖的 PR 单独成窗**：
  - 合并前在分支上跑过 T1（以及声明涉及的档）并把结果贴进 PR；
  - 合并后主干立即跑一次 T1，不和别的 PR 攒在同一个窗口里。
- **声明与实测不符就拦**：声明「数学不变」却不逐位，或者声明范围以外的行变了，PR 退回，改声明或查清原因后重跑。
  - 声明是作者对改动的理解，实测对不上，要么有 bug、要么理解错了，两种都不能放行。

### 声明决定每一行怎么判

声明决定每一行怎么判（行号见第四节）：

| 行 | 数学不变 | 会改数值 · 执行级 | 会改数值 · 数学级 | 升级依赖 |
|---|---|---|---|---|
| 输入与环境 R01–R07 | 逐位 | 逐位（声明改的配置字段除外） | 同左 | 逐位（声明的版本、开关字段除外） |
| 数值结果 R08–R10、R12–R16 | 逐位 | 声明范围内：`calibrated`（TPU 执行噪声）；范围外：逐位 | 声明范围内：只报，由对齐门拦；范围外：逐位 | 先要求逐位；不逐位按执行级判，并做第九节的归因 |
| 健康、覆盖、自检、续训 R11、R17、R23、R24、R27 | 恒为硬门 | 同左 | 同左 | 同左 |
| 编译产物 R18–R20 | 与 LKG 逐项相等 | 声明的变化以外相等 | 同左 | 同左 |
| 只报 R21、R22、R28 | 只报 | 只报 | 只报 | 只报 |
| 对齐门 R25 | 继承 LKG | 不变差 | 不变差 | 不逐位时：不变差 |

**「不变差」**：对 GPU golden 的三个量（带符号均值取绝对值、MARE、最大单步），新值 − LKG 的值 ≤ 同一指标的 TPU 执行噪声上限。

- 三个量只对**一份事先指定的 golden**（基线，惯例取 `-a` 那份；目录里写 `multi_golden` 的 `params.baseline`）算。
  - 其余 golden 只用来组噪声带，不取平均、不取各份里最差的一份（[`judging.md`](judging.md)「golden 怎么用」）。
- 比执行噪声还小的变化分不出好坏，不判；超出的就是变差。
- 执行噪声还没标定时判 `inconclusive`，人工看。

## 四、验收清单

每行一项检查。名字、个数、数值由实例文档按模型填。

- **门类**：逐位 = 字节相同；容差 = 指标对门槛；计数 = 整数相等或在区间内。
- **门槛**一栏先写「数学不变」时的门槛，其余声明怎么变见第三节的表；只在这一行有特殊处理时另写。
- **档位**见第六节。

### 逐行说明：比什么、失败时先查什么

#### R01–R07 · 运行与输入

- **R01 运行完整**
  - 比什么：完成步数 = 计划步数；运行目录有 `DONE`；`metrics.jsonl` 步号连续不重复；中途重启次数 = 0
  - 失败时先查：作业日志。
    - 起不来、被抢占、超时、鉴权失效 → **基础设施**，重跑；
    - 编译失败、OOM、程序报错且重跑复现 → **代码回退**，照第八节二分，判据是「能不能跑完」
- **R02 固定输入**
  - 比什么：权重清单、数据清单、档位配置文件的 sha256，检查项目录的内容指纹（改注释与说明文字不算，见 `result-schema.md` 注 2），对档位钉死的值
  - 失败时先查：
    - 挂载的是另一份数据或权重；
    - 档位配置或目录的检查被改了——改它们就是改档位定义，要在同一个 PR 里更新钉死的 sha256（目录是内容指纹）并写明原因
- **R03 数据指纹**
  - 比什么：每步每 rank 每 microbatch 的 `tokens`、`labels`、`loss_mask`、`position_ids` 的 sha256；每步非 padding 总数（`data_fingerprint`，全部步，不抽样）
  - 适用 PR 类型：全部；改数据管线的 PR 另开档位
  - 失败时先查：数据管线、打乱种子、多线程读取的竞态（表现为个别步的 token 数不同）、主机数与切分
- **R04 版本**
  - 比什么：镜像 digest；jax、jaxlib、libtpu、flax、optax、kernel 库、checkpoint 库的版本；训练代码与 janus 的 commit
  - 失败时先查：镜像标签漂了（只认 digest）；依赖没钉版本
- **R05 编译与运行开关**
  - 比什么：`XLA_FLAGS`、`LIBTPU_INIT_ARGS`、相关环境变量、框架展开后的完整配置。
    - **编译进程和运行进程各取一份**（提前编译时两者是不同进程），两份互比，再各自对 LKG 比
  - 失败时先查：提前编译与运行用了两套开关；模板渲染漏了变量；上游改了默认值
- **R06 「必须等于」断言**
  - 比什么：dropout = 0、实际生效的权重衰减、学习率曲线参数、MTP 开关、跳步开关、路由偏置更新率、矩阵乘精度等（`config_diff` 的 `equals`；清单在实例文档）
  - 失败时先查：上游改了默认值；调度器覆盖了配置值
- **R07 加载后状态**
  - 比什么：训练前全部状态的 sha256：FP32 主权重、优化器状态、路由偏置（全量）。
    - **不用 BF16 清单**：FP32 主权重上不到半个 BF16 格的差，转成 BF16 就看不见
  - 失败时先查：权重加载与转换代码；dtype（R18）

#### R08–R16 · 第 1 步、序列、K 步后状态、路由

- **R08 第 1 步 loss**
  - 比什么：第一个训练步（步号按 `meta.steps.first`）的 `lm_loss`，以及开了的分项 loss
  - 失败时先查：依次排除 R02–R07，剩下的是前向路径的改动
- **R09 第 1 步范数**
  - 比什么：第一个训练步的 `raw_grad_norm`（裁剪前）、`param_norm`（更新后）
  - 失败时先查：R08 相同而这里不同：反向或优化器的改动
- **R10 第 1 步张量**
  - 比什么：全部参数梯度、更新后 FP32 主权重、两个动量、更新后路由偏置；另报 ULP 分布（只诊断）
  - 门槛：`exact`；执行级时 `calibrated`，噪声来自扰动臂的第 1 步抓数
  - 失败时先查：第一个不同的张量在哪层、前向还是反向（串跑找台阶）；前提是 R11 通过
- **R11 抓数钩子自检**
  - 比什么：抓数步上，加钩子的程序与生产程序输出的训练状态、loss、范数逐叶子比（`meta.hooks.selfcheck`）；往下训练一律用生产程序的输出
  - 门槛：`exact`。
    - 建立 LKG 时用 `--probe-tiers` 选一档自检逐位的抓数档位，之后一直要求逐位；
    - 一档都不逐位的平台，R10、R16② 只报，标为诊断值
  - 失败时先查：某个改动改变了钩子附近的融合决策：先确认 R15 逐位（生产轨迹没变），再换一档抓数
- **R12 loss 序列**
  - 比什么：窗口内逐步 `lm_loss`：首步差、带符号均值、MARE、最大单步及步号；**第一个不同的步**
  - 门槛：`exact`（四个量都是 0）；执行级 `calibrated`；另有单步硬上限（表后）
  - 失败时先查：
    - 第一个不同的步是第 1 步 → 看 R08；更晚 → 看那一步的数据（R03）和路由（R16）。
    - **R15 逐位而这里不同** → 只改了 loss 的统计或记录方式，训练没变。
    - 步号整体错位 → 步号约定变了（`auto_offset` 探测）
- **R13 梯度范数与参数范数序列**
  - 比什么：逐步 `raw_grad_norm`、`param_norm` 的四个量与第一个不同的步
  - 失败时先查：梯度范数先于 loss 变：反向、裁剪、优化器
- **R14 学习率序列**
  - 比什么：逐步 `lr`、`wd`（实际生效值）
  - 失败时先查：调度器配置；步号约定（从 0 还是从 1 起）
- **R15 K 步后状态**
  - 比什么：最后一步全部状态的 sha256：FP32 主权重、两个动量、路由偏置（全量，不用 BF16 清单，理由同 R07）
  - 失败时先查：R12–R14 都相同而这里不同：改到了不影响 loss 的状态（如某组参数的更新被冻结）
- **R16 路由**
  - 比什么：
    - ① 逐层逐步的路由偏置均值、标准差，专家负载变异系数（`router_stats`）；
    - ② 抓数步每层 top-k 选中集合不同的 token 数（翻转数，`discrete_agreement`）与翻转 token 第 k、k+1 名的分差
  - 门槛：① `exact`；② 翻转数 = 0。
    - 执行级时：①`calibrated`；② 翻转数 ≤ 扰动臂对里的最大翻转数，且翻转 token 分差的最大值 ≤ 扰动臂对里的同一量
  - 失败时先查：偏置更新率、偏置 dtype（R18）、路由 GEMM 的精度（R20）

#### R17–R23 · 健康、dtype、编译产物、步时、覆盖

- **R17 非有限值与跳步**
  - 比什么：loss、梯度范数、参数范数里非有限值的步数；跳过更新的步数；突跳步数（某步超过前 20 步中位数的 10 倍，`health_signals` 默认参数）
  - 失败时先查：梯度范数先于 loss 报警（第一阶段埋 NaN 时梯度范数早一步变非有限）；按第一处非有限值的步与层定位
- **R18 dtype 清单**
  - 比什么：全部状态按 dtype 计数，并按规则逐个核对（`dtype_manifest`；没被规则覆盖的名字报 `error`）
  - 失败时先查：小张量（如路由偏置）被存成 BF16；优化器状态 dtype 被降
- **R19 假 FP32**
  - 比什么：更新后 FP32 主权重与两个动量里，非零有限元素低 16 位全为 0 的比例（`fake_fp32`）
  - 门槛：每个张量 ≤ 0.99（来源：[`checks/fake_fp32.md`](checks/fake_fp32.md)）
  - 失败时先查：某处先舍入成 BF16 再升回 FP32
- **R20 编译产物计数**
  - 比什么：生产训练步**实际执行的那个可执行文件**的优化后 HLO，按规则计数（`artifact_check`；规则在实例文档）：
    - 低精度乘法个数；
    - 路由 GEMM 的操作数 dtype 与精度；
    - 分组 GEMM 与注意力 kernel 的调用数；
    - 随机数算子个数；
    - 要求保存的中间结果（如路由结果）是否被保存
  - 失败时先查：开关名义上开着、实际没生效（被静默回退）；编译器换了实现
- **R21 编译产物指纹**
  - 比什么：优化后 HLO 去掉元数据后的 sha256
  - 失败时先查：不拦。逐位不变的性能 PR 也常改它。给二分和归因做线索
- **R22 步时与显存**
  - 比什么：稳定窗口内步时中位数（去掉前几步与开 profiler 的步）；峰值 HBM；编译期临时区大小
  - 门槛：只报。偏离 LKG 超过阈值且连续两次，开性能 issue。
    - 阈值「待标定」：同一提交在该档跑 ≥ 5 次（可与首个 LKG 的双跑、对照臂合用），阈值 = max(2 × 这几次步时中位数的极差 ÷ LKG 步时, 1%)。
    - 1% 的下限是推断：再小的步时差一般不值得追。
    - 编译期临时区大小对同一程序是确定的，变了就报
  - 失败时先查：不拦。数值相同而步时变了，是性能回退，不是数值回退
- **R23 覆盖**
  - 比什么：每行实际比较的单元数（步、rank、microbatch、张量、层）= 期望数；目录里每一行都出了结论（`coverage`；没跑的行判 `error`）
  - 失败时先查：哪一行被跳过、哪个字段没写出；新加的层或张量没进期望清单

#### R24–R28 · 对照臂、对齐门、工具、续训、生产配置

- **R24 对照臂**
  - 比什么：今天重跑 LKG 的提交：R03、R08、R09、R12–R16 对 LKG
  - 档位：每天一次（T0 配置）；任何一档数值失败时，先用那一档的配置跑一次
  - 失败时先查：不逐位 = 环境变了：镜像、驱动、硬件（静默数据错误）、主机数。换一批机器重跑
- **R25 对齐门**
  - 比什么：对 GPU golden 的 loss、梯度范数、路由统计（`multi_golden` 等，与迁移验收同一窗口、同一分母）
  - 失败时先查：第十节：要不要回去重跑迁移验收的哪几级
- **R26 工具自回归**
  - 比什么：janus 版本变了时，用新版本重判 LKG 的运行目录：每行的指标与状态和旧版本相同；核心行的 `poison_selftest` 通过
  - 失败时先查：新版本改了某个检查的判法；改了要同 PR 改规格
- **R27 续训**
  - 比什么：第 K 步存档、恢复后接着训，重叠步对连续训练逐位（`overlap_replay`）
  - 失败时先查：checkpoint 库、存档的 dtype 与切分
- **R28 生产配置覆盖**
  - 比什么：生产配置里每个和数值有关的开关（精度、并行、重算、kernel 选择、低精度配方、编译开关），至少在一档里取同样的值
  - 门槛：没覆盖的开关数 = 0；不为 0 时每个缺口写进报告与实例文档。改生产配置的 PR 要同时补档位或登记缺口
  - 失败时先查：回归档位是从旧配置复制来的、没跟上生产配置

### 两条通用规则

**单步硬上限**：只报不拦的行（数学级声明范围内的 R12–R13、金丝雀档、低精度配方对高精度参照）仍有两条硬底线：

- 任何非有限值（R17）；
- 任何一步的相对差超过硬上限。
  - 硬上限 = 10 × 同窗口、同分母的 GPU 噪声最大单步。
  - 推断：远高于 2N 的 `fail` 线，健康的噪声碰不到；它只在噪声参照失效、过期或这一行只报时兜底，防止有限值的发散被放过去。
  - 没有 GPU 噪声的档（T3）用该档 TPU 执行噪声的最大单步 × 10。
  - 还没标定时只剩非有限值一条硬底线，报告里写明。

**比全精度原值，不比日志**：

- 序列一律读 `metrics.jsonl` 的原值（FP32 原值转成 float64 写出，往返无损），不从打印的训练日志里解析。
- 日志只打几位小数，「打印出来的每一位都相同」不等于逐位相同（步日志只打印 3 位小数，就造成过这种假象）。

## 五、TPU 自噪声：怎么标定

逐位不过、又声明了「执行级」时，需要一把 TPU 自己的尺子。TPU 同程序重跑噪声为 0，所以用**扰动臂**：只改执行方式、不改数学的运行。

### 选臂与三关

**选臂**。

- 候选：remat 档位（要求保存的中间结果不变，只改重算范围）、编译器片上内存上限、注意力 kernel 的块大小、调度类开关。
- 已知**不能**当臂的：梯度累积切分、专家并行度、不保存路由结果的整层重算。
  - 第一阶段 GPU 上证明它们改数值超出噪声（[`00-gpu-noise-and-drills`](../../models/hunyuan3/alignments/00-gpu-noise-and-drills/README.md)「四、只换执行方式，哪些仍逐位」）。

每个候选臂过三关才进参照：

1. **臂自己确定**：同一个臂重跑两次逐位。
2. **只改了执行**：R02–R07、R14、R18、R20 对基线逐位或计数相等。
   - R20 变了说明臂改动了算子种类或精度，不是只改执行。
3. **差在舍入量级**，分两半：
   - **loss**：窗口内 loss 序列对基线的三个量，都不大于迁移验收里 GPU 自己重跑的噪声上限（同一窗口）。
   - **第 1 步参数梯度**：臂离 FP64 整步参照不比基线远，全部张量按能量合起来 R = rel_L2(臂, FP64) / rel_L2(基线, FP64) ≤ 1.2（参照由 `models/hunyuan3/analysis/fp64_step.py` 算）。
     - 不拿第 1 步梯度直接和 GPU 第 1 步噪声比（2026-11-06 改）。GPU 重跑第 1 步路由从不翻转，那把尺子对近似平局的路由翻转宽度是 0（[`judging.md`](judging.md#第-1-步张量两侧执行噪声的并集)「第 1 步张量：两侧执行噪声的并集」；该节的并集是混元 3 当时的判法，这里比 FP64 的做法不受影响）。
     - 而只改执行方式的臂会翻：上游激活的 BF16 舍入跟着融合与切块变，近似平局的路由就落到另一边。混元 3 当前配置 v5p 上，改片上内存上限的臂对基线，第 3 层专家 0 的梯度差 0.080；只改 splash 分块的臂之间也有 1.4e-3。两者都远大于 GPU 第 1 步的梯度噪声上限 5.34e-4。
     - 这正是噪声参照该含的执行级差异，不说明臂改了数学。判它有没有改数学，看它是否让第 1 步梯度整体离精确更远：上面 6 个臂 R v5p 1.001 – 1.008、v7x 1.003 – 1.039，逐张量最大 1.0 – 2.9，大的都是经过路由的张量（[`arms-step1-vs-fp64.json`](../../models/hunyuan3/regression/results/arms-step1-vs-fp64.json)）。
     - 所以扰动臂**会扰动近似平局的路由**。拿它们造噪声带没问题，但要写明：TPU 执行噪声里包含路由翻转，GPU 第 1 步噪声里不包含。
   - 这个上限取**至少 10 次**默认设置 GPU 运行的两两组合（≥ 45 对）的最大值，不能只用 3 份 golden 的 3 对。
     - 几个样本的最大值会把上限压低，带符号均值尤其明显。
     - 混元 3、窗口 `1:1001`：3 对的上限 3.1e-5，10 份运行 45 对的上限 5.4e-5（`models/hunyuan3/regression/results/README.md`）。
   - 参与的运行必须和 golden 是同一种设置（只许日志、抓数这类不进训练图的选项不同）。
     - 换了重算或路由回放的运行是另一种设置，不能混进来。
   - GPU 自噪声是这个模型「舍入级差异」的现成尺度，比它还大的差就不算只改执行。
   - 前向激活不用这一条：GPU 默认设置下第 1 步前向逐位可复现，那里的 GPU 噪声上限是 0，当不了尺子。
     - 前向只看 ULP 分布（只诊断）和路由翻转 token 的分差。

### 凑够参照对

- 同一个臂重跑两次逐位，算不上一对（工具会剔除，见 `noise_dropped`）。
- 参照对来自**不同配置**之间：基线加 k 个臂，共 k + 1 份运行，两两成 (k + 1)k / 2 对。

照 [`judging.md`](judging.md)「参照要几对」：

| 参照对数 | 运行份数 | 能给出的判定 |
|---|---|---|
| < 3 | ≤ 2 | 最多 `inconclusive` |
| ≥ 3 | 3（基线 + 2 个臂） | 能判，但纯噪声的被测约每 4 次就有 1 次超上限（1 / (n + 1)，n = 3） |
| ≥ 15 | 6（基线 + 5 个臂） | 正式启用这一档的 `calibrated` 判定的下限 |
| ≥ 28 | 8（基线 + 7 个臂） | 最大单步这类极值统计量建议的数 |

- 单开关不够时用组合：3 个二值开关全组合是 8 份运行、28 对；组合里每一份都要过上面三关。
- 参照对共用运行，不是独立样本，这一点和 GPU 侧一样。

### 维护参照

**查参照齐不齐**：看留一法互判（`noise_loo`）。

- 某个臂一条撑起上限，或者对其余臂有持续偏移（|带符号均值 / 标准误| 明显大于其他对），说明它不只改了执行，剔掉。

**一份噪声参照绑定什么**：平台、档位配置（配置文件 sha256）、依赖集合（R04 全部字段）。

- 任何一样变了，这份参照作废，用它的 `calibrated` 行降为 `inconclusive`，直到重标。
- v5p 的参照不给 v7x 用。

**什么时候重标**：

- 接受一次「升级依赖」或「会改数值 · 数学级」之后（基线变了）；
- 档位配置变了；
- 新平台上线。

标定花的是 (k + 1) 次该档的运行，结果写进实例文档，带运行名。

## 六、档位与节奏

同一套档位用在每个平台上；步数、切片、时长写在实例文档的平台档案里。

| 档 | 触发 | 模型与规模 | 步数 | 抓张量 | 跑哪些行 | 用途 |
|---|---|---|---|---|---|---|
| **T0 冒烟** | 每次合并到主干；PR 上可手动触发 | 截层模型，最小切片 | 几十步 | 否 | R01–R09、R14、R15、R17、R18、R20–R23 | 几十分钟内发现「跑不起来」「第 1 步就变」 |
| **T1 主力** | 每 2–4 小时，主干有新提交才跑 | 截层模型，最小切片 | 与迁移验收的 golden 同窗口 | 否 | T0 全部 + R12、R13、R16①、R25 | 主力回归门；窗口短，出事时只在几个提交里找 |
| **T2 每日** | 每天一次 | 同 T1；另加生产用的各并行变体，每个变体一份 LKG | 同 T1 | 第 1 步 | T1 全部 + R10、R11、R16②、R19、R27 | 张量级逐位；只在某种并行下出现的问题 |
| **T3 生产形状** | 每天或每周 | 生产层数、生产切片 | 100–200 | 否 | R01–R09、R12–R15、R17、R18、R20–R23 | 只在深层、大规模出现的问题。没有同规模的 GPU golden，不跑 R25 |
| **T4 低精度配方** | 配方启用后每天一次 | 低精度配方（如 FP8）的生产配置截层 | 同 T1 | 第 1 步 | 对**本配方自己的 LKG**：同 T2；对高精度 LKG：只报 + 硬上限 | 低精度配方自己也是确定的，可以逐位回归；它和高精度的差只当观测 |
| **金丝雀** | 每天一次 | T1 配置，依赖换成上游最新构建（libtpu 每日构建、kernel 库主干） | 同 T1 | 否 | 同 T1，全部只报 + 硬上限 | 正式升级前就知道新依赖会不会改数值。不更新 LKG、不拦 |
| **对照臂** | 每天一次；任何一档数值失败时先跑 | 失败那一档的配置（例行时用 T0），LKG 的提交 | 同该档 | 同该档 | R24 | 把「环境变了」和「代码变了」分开 |
| **标定** | 第五节列的时机 | 该档配置 + 扰动臂 | 同该档 | 同该档 | 只产出噪声参照 | 给执行级判定和「不变差」提供尺子 |

### 排程

- 几档错开时间、共用切片；同一档用并发组保证不重叠；每次新建作业，结束后清理。
- T0 每次合并都跑，第 1 步到第几十步就变的改动能直接落到一个合并上。
  - 更晚才显出来的，靠 T1 的短窗口和二分。

**资源估算**：每平台每天 ≈ T0 × 合并次数 + T1 × (24 ÷ 间隔小时数) + T2 × 并行变体数 + T3 + T4 + 金丝雀 + 对照臂，每项乘实测时长。

- 没实测前写「待实测」，实测后写运行名。

### 手动阶段

加速器预算不够按节奏跑时，上表的节奏保留为目标。

- 各档手动触发，用同一套目录、同一套判法、同样的报告。
- 手动阶段没有「该跑没跑」的核对，所以每次手动运行都必须出完整报告。
- 数值失败时对照臂随那一次补跑。
- 排程等有预算再上。实例文档写明现在处于哪个阶段。

## 七、LKG：谁能当、怎么换

### 登记

**LKG 按「模型 × 平台 × 档位 × 并行变体」各一份**，登记在 `models/<模型>/regression/lkg.yaml`。

- 登记项：运行名、训练代码提交、日期、依赖集合、镜像 digest、档位配置 sha256、换代理由、批准人、结果位置（占位写法，不写桶名）。
- 旧 LKG 不删，二分和翻案要用。

### 谁能当

**首个 LKG**：同一提交在这一档跑两次，两次逐位相同，且都满足下面的候选条件。

- 这一步就是这一档在这个平台上「同程序重跑逐位」的实测。

**一次运行能成为 LKG 候选，要同时满足**：

1. 跑完全部计划步数、没有中途重启（R01）；取消、超时、失败的运行永远不当 LKG；
2. 本档全部硬门 `pass`，没有 `error`，覆盖完整（R23）；
3. 当天的对照臂逐位（R24）；
4. 抓了张量的档，钩子自检逐位（R11）。

### 怎么换

- **数值没变**（回归门逐位通过）：LKG 指针自动前移到新提交。
  - 数值完全相同，前移只是更新「最近一次验证过的提交」。
- **数值变了**（会改数值、升级依赖）：**不自动换**。由实例文档写明的批准人批准。
  - 批准时附：PR 号与声明、回归门各行的变化、对齐门「不变差」的结果、（升级依赖）第九节的归因结论。
  - 批准后那次运行成为新 LKG，`lkg.yaml` 记一条换代记录。
  - 同一改动影响的每个平台、档位、并行变体各自换代，各记一条。
- 噪声参照已作废时（第五节）不批准换代，先重标。

### 红灯期间

某一档失败、还没结论时，这一档的 LKG 不动，后面的运行仍对同一个 LKG 比。

- 报告标「窗口内有未结的失败」，并看第一个不同的量变没变，分清是同一个原因还是又来了一个。
- 会改数值、升级依赖的 PR 在红灯期间不合并：它们要对一个绿的 LKG 才判得清。
- 数学不变的 PR 照常合并：它们仍按逐位对同一个 LKG 判。
  - 红灯期间合进来的每一个，都看第一个不同的量有没有变。
  - 变了就是又来了一个原因，单独分诊。

## 八、失败了怎么办：分诊与二分

**第一步：分类**，报告首行写清是哪一类：

| 类 | 判据 | 处理 |
|---|---|---|
| 基础设施 | R01 不过：作业没起来、被抢占、超时、鉴权失效、集群异常 | 重跑，不判数值。连续两次没出结论就报警——「没有结论」不能静默当成「没问题」 |
| 代码（跑不完） | R01 不过，且是编译失败、OOM、程序报错，换机器重跑仍复现 | 二分，判据是「能不能跑完」 |
| 环境 | 对照臂 R24 不逐位 | 换机器重跑对照臂；还不逐位，查镜像、驱动、硬件 |
| 工具 | janus 版本变了且 R26 不过；或某行报 `error` | 修工具，不动 LKG |
| 数值 | 有硬门不过，且对照臂逐位 | 二分 |

**第二步：二分**（数值类）。窗口：LKG 的提交到失败的提交。

1. **先分依赖还是代码**：R04、R05 有变化时，代码钉在 LKG 提交、只换依赖（或只换开关）跑一次。
   - 变了 → 依赖问题，转第九节的归因；
   - 没变 → 代码问题，往下。
2. **选最便宜的判据**：取失败运行里**第一个不同的量**。
   - 第 1 步 loss 不同就只跑 1 步；
   - 第 1 步相同、第 k 步才不同就跑 k 步；
   - 只有 R15 不同就跑满 K 步看状态。
   - 判据是这个量对 LKG 逐位相不相同，是 0 / 1 信号。
3. **在训练代码仓库上二分**：只走主干的合并提交（`git bisect start --first-parent`），`git bisect run <脚本>`。
   - 脚本返回 0 = 和 LKG 逐位相同。
   - N 个提交约 log₂N 次运行。
4. **定位到层**：在找到的提交和它的父提交上各跑第 1 步抓张量。
   - 串跑找台阶（第一个不逐位的层、前向还是反向，见 [`levels.md`](levels.md)）；
   - 再比两边的 R20 计数与 R21 指纹，看编译器换了什么。
5. **处理**：
   - 那个提交声明的是「数学不变」→ 回滚，或改声明后走「会改数值」流程；
   - 声明了「会改数值」但超出声明范围 → 退回作者。
   - 结论写进 issue。

## 九、升级 jax / libtpu / kernel 库

升级本身就是被测对象。按顺序：

1. **先看金丝雀**：上游新构建在金丝雀档跑过几天，已经知道会不会变、哪几行变。
2. **开「升级依赖」PR**，代码不动，只改版本（镜像 digest、锁文件、开关）。在分支上跑全部档位、全部平台、全部并行变体。
3. **逐位通过**：同「数学不变」，批准后各档 LKG 指针前移（依赖集合变了，`lkg.yaml` 照样记一条）；噪声参照因依赖集合变了要重标。
4. **不逐位，做归因**：
   1. **矩阵乘精度对照**：把矩阵乘精度临时调到最高档，新旧两版各跑一次 T0。
      - 最高档下逐位相同，说明差异来自矩阵乘的分块与累加顺序（编译器换了 codegen），属于执行级；
      - 仍不同，再往下查别的算子。
      - 这个对照只用于归因，不进生产配置。
   2. **关键算子回放**：路由 GEMM、注意力、分组 GEMM 等在新旧两版上对 FP64 比，新版不比旧版离 FP64 远（[`levels.md`](levels.md) 的 R-ratio）。
   3. **按执行级判**回归门（用旧依赖下标定的执行噪声）；对齐门不变差。
5. **重标噪声参照**，在新依赖下按第五节重做。
6. **批准换代**：每个平台、档位、并行变体各换一次 LKG，各记一条。
7. 升级不过时，钉回旧版本，在 issue 里写清哪一行、差多少、归因到哪。

## 十、和迁移验收的关系

日常回归只证明「和上一次验证过的 TPU 一样」。数值变了以后，「和 GPU 一样」要重新证明到哪一级：

| 回归里发生了什么 | 回去重跑迁移验收的哪部分 |
|---|---|
| 数学不变，回归门逐位 | 不用。对齐结论继承 LKG |
| 执行级，回归门 `pass` | 只要 R25 对齐门（L4）不变差 |
| 数学级 | L3 第 1 步（对 GPU golden，`calibrated`）+ L4；L3 变差时往下到 L2 逐层 |
| 改了数据管线 | L0 数据对拍（对 GPU 的数据指纹） |
| 改了权重转换、存档格式 | L0 `checkpoint_equal`（转换后逐张量逐位） |
| 升级依赖不逐位，或某个 kernel 换了实现 | L1 该算子回放（对 FP64 与 GPU）+ L3 + L4 |
| 换平台、改模型层数、开新配方（如 FP8） | 不属于日常回归：开新的对齐实践文件夹，从 L0 走一遍（[`layout.md`](../dev/layout.md)「新对齐实践的命名」） |

重跑的结果进对应对齐实践的 `results/`，不进回归目录。

## 十一、报告

每次运行一份。首屏回答「过没过、哪一类、先看哪」：

```
[T1 · v5p-8 · 2026-11-05 14:00] 数值 FAIL
窗口：LKG <运行名>@<提交> → <提交>（3 个 PR：#a 数学不变、#b 数学不变、#c 数学不变）
依赖与开关：无变化（R04、R05 逐位）      对照臂：逐位（当天 09:00）
第一个不同：R08 第 1 步 loss
硬门：fail 3 / pass 22 / inconclusive 0 / error 0      只报：R21 指纹变；R22 步时 +0.4%
下一步：二分，判据为第 1 步 loss（每次 1 步运行）
```

示例里的时间与计数只为说明格式，不是测量值。往下依次是：

1. 每行的状态与关键数（编号同清单）：
   - 逐位行写「相同 / 不同 + 第一处不同的位置」；
   - 容差行写被测值、上限、r；
   - 计数行写实际数与期望数。
2. 逐步曲线：被测对 LKG 的逐步差，标出第一个不同的步。
   - 对齐门跑了的话，再画被测、LKG 各自对 GPU golden 的逐步差。
3. 多平台时，各平台同一提交的 R25 结果并排一行（只报，不比平台之间）。
4. 运行与产物（POC 项目里的路径）、janus 版本、目录的内容指纹。

- 结果 JSON 与曲线存到 POC 项目的存储桶，路径 `<模型>/regression/<平台>/<档>/<日期>/<运行名>/`。
- 数值类失败开 issue 记下来，贴首屏和第一个不同的量。

## 十二、常见误判

- **门保护的不是生产图**。回归跑的必须是投产的那个程序：同一套编译开关、同样的 HLO 改写。
  - 提前编译与运行各用一套开关，或者回归开了生产没开的图改写（改写会改变归约顺序），门就在保护另一张图。
  - R05 两份开关互比、R20 读实际执行的可执行文件、R28 核对生产配置覆盖，都是为此。
- **兄弟档位的配置漂了**。新档位从旧档位复制过来，旧档位后来改了并行切分或重算设置，新档位没跟上，会稳定地误报。
  - 每档配置的 sha256 进 R02，档位之间共用的部分只写一处。
- **没有结论被当成通过**。轮询脚本吞掉鉴权错误、超时被记成「取消」，一次真实的超线就丢了。
  - R01 不过报「无结论」，连续两次报警。
  - 该跑没跑（调度没触发、作业一直排队）同样是无结论：每天按节奏核对每档应有的运行数和实际数，少了就报警。
- **开关的实际取值和报告说的相反**。「不传参数 = 关闭」只在默认值真是关闭时成立。
  - 报告里的开关取值一律从运行进程里读出来（R05），不从调用方的参数推断。
- **开关开着但没生效**。配置写着开、编译产物里没有（被静默回退、统计没收集到、阈值从没触发）。
  - 逐位回归看不出来——两次都没生效，当然逐位。
  - R20 按产物计数。
- **只报的门把 NaN 也放过了**。不拦的行对非有限值和单步硬上限照样硬失败。
- **门槛从一次基线乘倍数定**。一次基线 × 2–3 定出的门槛，下一次正常波动就会贴线。
  - 逐位门不需要门槛；容差门的门槛来自扰动臂的参照对，对数够（第五节）。
- **失败了就放宽门槛**。放宽要附新的噪声数据，写明改前改后、触发的运行、旧口径下这次过不过。
- **持久编译缓存**。回归运行不读共享的持久编译缓存，或者先证明缓存命中时 R20、R21 与冷编译相同。
  - 否则跑的可能是另一套开关编出来的可执行文件。
